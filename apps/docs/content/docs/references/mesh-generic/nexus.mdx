> Status: live `/stream` adapter (`packages/tile-server/nexus-live.js`) and offline converter
> (`packages/nexus-to-3dtiles/`, through `3dtiled <file.nxs|nxz> <outDir>`). Reader in pure JavaScript, written from
> the format's layout; the compressed nodes of an `.nxz` are decoded by the MIT JavaScript decoders Nexus and Corto
> publish, vendored unchanged. Read in full on four public `.nxz` files (2 841 nodes, 58.4 M triangles, 2 569
> textures); plain `.nxs` and the older meco compression are covered by synthetic files and the vendored decoder
> only. Not supported: `DEEPZOOM` files (nodes in a `_files/` folder beside the `.nxs`).

[Nexus](https://github.com/cnr-isti-vclab/nexus) is the multiresolution mesh format of the Visual Computing Lab of
CNR-ISTI (Pisa): the format [3DHOP](https://3dhop.net/) streams, what `nxsbuild` writes from a PLY and `nxsedit`
compresses, what MeshLab exports. It is the usual format of the cultural-heritage world's large scans, a statue or
a building front of a few million triangles, one object in its own frame, with no georeference.

```
GET /stream/tileset.json?format=nexus&url=<….nxs | ….nxz>[&dag=levels|paths][&ge=<factor>]
GET /stream/tile/<node>.glb?format=nexus&url=<same>
```

`url` is an http(s) URL or a local path. `format=nexus` is detected from a URL ending in `.nxs` or `.nxz`. The
tileset comes from two range reads (the header, then the tables), a tile from one or a few more (the node's bytes
and the textures its patches name). `dag` and `ge` are explained under [the tree](#the-tree).

```
3dtiled model.nxz out/                         offline: out/tileset.json + out/tiles/node_<i>.glb
3dtiled model.nxz out/ --dag paths --ge-scale 4 --workers auto
```

## The file

One file, little-endian, every data offset a multiple of 256 bytes. There is no specification document; the layout
is that of `src/common/dag.h` and `signature.h` of the Nexus sources and of its JavaScript loader, and
`packages/nexus-to-3dtiles/src/nexus-reader.js` is written from this description.

| Part | Bytes | Holds |
|---|---|---|
| Header | 88 | magic `Nxs ` · version · vertex and face counts (u64) · the **signature** · counts of nodes, patches, textures · the model's sphere |
| Signature | 36 (in the header) | the vertex element, 8 × (type, count) for coord, normal, color, uv, data0…3; the face element, the same 8 for index, …; flags: `PTEXTURE` 1, `MECO` 2, `CORTO` 4, `DEEPZOOM` 8 |
| Node × n | 44 | data offset (÷ 256) · vertices and faces (u16, so a node holds at most 65 535 of each) · **error** (model units) · cone (i16 × 4) · **sphere** (saturated: it holds every finer node's) · tight radius (the node's own) · first patch |
| Patch × n | 12 | the finer **node** this run of triangles is refined by · the triangle index the run ends at · the **texture** it uses (`0xffffffff`: none) |
| Texture × n | 68 | data offset (÷ 256) · a 4 × 4 matrix (unused by the viewer) |
| node data | | per node: coords f32 × 3, uvs f32 × 2, normals i16 × 3, colours u8 × 4, then faces u16 × 3 (the components the signature lists, in that order); in an `.nxz` a Corto stream (or, in old files, a meco stream) decoding to the same arrays |
| texture data | | per texture: one image file as it is, JPEG from `nxsbuild`, zero-padded |

The last node and the last texture entry are **sinks** with no data, there to end the offsets and the patch
runs of the entry before them. The patches of node *i* are `[first_patch(i), first_patch(i + 1))`, and they
partition its triangles: patch *p* covers the triangles from the previous patch's end to its own.

The nodes form a **DAG from coarse to fine**. Node 0 is the coarsest; a node's patches name finer nodes; a leaf's
patches name the sink. Nodes are numbered coarse to fine, so a parent's index is always below its children's, and
the roots are the nodes no patch names (`nroots`, 1 in every file seen). A finer node is named by the patches of
**several** coarser nodes: 171 of the gargoyle's 187 nodes have more than one parent, up to 10. This is batched
multi-triangulation: each level is a complete mesh of the whole model at one resolution, cut into nodes along
boundaries that the next level's nodes do not share, so that the viewer can draw any mix of levels without a crack.
The viewer draws a node while `error / (the size of a pixel at its distance)` is above its target (2 px by default),
and a coarser node draws only the patches whose finer node is not drawn.

## The tree

3D Tiles has no DAG: a tile has one parent, and `REPLACE` swaps a tile's content for all of its children at once. A
node drawn once in Nexus whatever the number of its parents would, under each of them, be drawn several times. Two
mappings are offered (`packages/nexus-to-3dtiles/src/nexus-tileset.js`, shared by the live adapter and the converter).

**`dag=levels`, the default**, cuts the DAG by level. Every node of level *k* is a tile with content under a
contentless level tile L*k*; the level tiles form a chain L0 → L1 → …; all the tiles that must switch together (the
nodes of level *k* and L*k*+1) are given the **same** bounding sphere (the model's) and the **same** geometric
error, so that a client decides them in the same frame, and a node tile refines through one empty child, which is
how it disappears when its level does. Each node tile keeps its own sphere as `content.boundingVolume`, what a
client culls by, so a close view loads and draws only the nodes in front of the camera. What is lost against Nexus
is the choice of a level per node by distance: the level is the same for the near and the far side of the model,
as for any single-mesh LOD. For an object of a few million triangles that is what Nexus models are, this is the
right trade: no overlap, no crack, one tile per node.

**`dag=paths`** keeps the DAG's own edges and writes a shared node under each of its parents, one tile per
root-to-node path, the same GLB referenced from each. The level is then chosen per node by distance, as in Nexus,
but a node reached through several refined parents is drawn once per path, and when only one parent is refined the
fine node overlaps the other parent's coarse patch. The number of paths is what makes it unreasonable past a shallow
DAG: 130 for the 28-node shell, 2 322 for the 85-node dragon, 25 202 for the 187-node gargoyle and 76 million for
the 2 541-node bust (which the server refuses to write; `nexusStats().paths` counts them).

**Geometric error.** Nexus refines while `error / pixel size` is above 2 px; a 3D Tiles client refines while
`geometricError / pixel size` is above its maximum screen-space error, 16 px by default. The same metric, so
`geometricError = (16 / 2) × error` reproduces Nexus's choice; `ge=` (`--ge-scale`) is that factor, default 8. By
levels, a level's error is the largest of its nodes', scaled.

**Frames.** A Nexus model is in its own frame, Y up as its viewer and MeshLab have it, and glTF is Y up too, so a
node's vertices are written as they are. A 3D Tiles client turns glTF's Y up into the tile frame's Z up,
(x, y, z) → (x, −z, y), so the spheres are written in that frame. The tileset carries no transform; `&lon=&lat=`
placement composes on top as for the other local formats.

## The tile

One node → one GLB (`packages/nexus-to-3dtiles/src/nexus-glb.js`, glTF-Transform): positions as the file has them,
the int16 normals made unit floats, the RGBA bytes as a normalized `COLOR_0`, the uvs with v flipped (Nexus's v
points up the image, glTF's down). A node's triangles are grouped by patch and a patch names a texture, so there is
one primitive per run of patches with the same texture (one, in every node seen) and the image is embedded as the
file holds it, a JPEG. A textured node drops its colours, as the Nexus viewer draws the texture alone then. The
material is unlit-looking (metallic 0, roughness 1), as glTF's default material renders a scan black.

Decoding an `.nxz` node is the one piece of code not written here: `vendor/corto.js` (Corto's MIT decoder) and
`vendor/meco.js` (the older decoder of Nexus's own loader, MIT) are vendored unchanged, with their licences. Nothing
of Nexus's C++ (GPL) is used. The decode runs on the server's thread, or on a tile worker when `TILED_WORKERS` is
set, as for the other mesh formats.

## Datasets

Every host answers `Range`. The first two columns are the viewer's presets. Numbers are the tables' (nodes without
the sink, triangles as the header counts them, at the finest level the leaves' sum).

| Preset | File | Size | Nodes / levels / leaves | Triangles (finest level) | Attributes | Terms |
|---|---|---:|---|---:|---|---|
| Gargoyle | [gargo.nxz](https://raw.githubusercontent.com/cnr-isti-vclab/3dhop/master/examples/models/gargo.nxz) (3DHOP's example) | 7.3 MB | 187 / 9 / 96 | 3 966 820 (1 987 410) | normals, colours | 3DHOP's [examples](https://github.com/cnr-isti-vclab/3dhop), GPL for the code; the model is the lab's sample |
| Unio hainesianus shell | [shell.nxz](https://huggingface.co/datasets/JulyTheMonth/NexusDataset/resolve/main/shell.nxz) | 40.2 MB | 28 / 7 / 13 | 541 840 (273 062) | normals, colours, uvs, 28 JPEGs | Smithsonian 3D, CC0, packed as Nexus in the `JulyTheMonth/NexusDataset` Hugging Face dataset |
| Stanford dragon | [dragon.nxz](https://huggingface.co/datasets/JulyTheMonth/NexusDataset/resolve/main/dragon.nxz) | 3.5 MB | 85 / 8 / 41 | 1 735 694 (871 306) | normals | Stanford scanning repository, non-commercial use |
| George Washington bust | [bust.nxz](https://huggingface.co/datasets/JulyTheMonth/NexusDataset/resolve/main/bust.nxz) | 241.6 MB | 2 541 / 13 / 1 264 | 52 116 066 (26 062 988) | normals, colours, uvs, 2 541 JPEGs | Smithsonian 3D, CC0, same dataset |

All four are version 2, Corto-compressed, with one root, errors that decrease along every patch, spheres that nest
and a layered DAG (no patch skips a level), so every one is written by levels. The other models 3DHOP ships
(Laurana, Capsella, Ercolano) are on the same GitHub path and read the same; the Nexus repository itself holds no
sample file.

Measured on 2026-11-11 from the worktree's server: the gargoyle's tileset in 5.8 s (two range requests to GitHub's
raw host, where a tile of 150 to 580 KB then takes 0.5 to 1.1 s); the shell's in 11 s and a textured leaf (1.4 MB
GLB, a 1 MB JPEG inside) in 22 to 36 s, which is the Hugging Face CDN's speed from here that day (1 MB in 25 s by
curl, 1 to 5 s before the first byte of any request), not the adapter's. Offline, the dragon converts in 0.7 s into
85 GLBs, 32 MB.

## Limits

- **One level for the whole model** by default (above). `dag=paths` restores the per-node choice at the cost of
  duplicated draws; neither is Nexus's exact behaviour, which no tree can carry.
- **Textures are passed through** as the file holds them (JPEG), one image per primitive, never atlased or
  resized; a node of the bust carries its own 1 MB JPEG, so a textured tile is as heavy as its image.
- **`DEEPZOOM`** files, whose nodes sit in a folder beside the `.nxs`, are refused with an error.
- **Meco** (the compression of `.nxz` files written before Corto, 2016) is decoded by the vendored decoder but was
  met on no public file; **plain `.nxs`** likewise on synthetic files only.
- The per-vertex `data0…3` attributes of the signature are skipped; the face element's normals, colours and uvs
  (never written by `nxsbuild`) are not read.
- No georeference: a Nexus file has none, so the tileset has no transform unless `&lon=&lat=` is given.

## Tests

`packages/tile-server/nexus.test.js`, 12 tests without the network: the reader over a synthetic `.nxs` written by
`packages/nexus-to-3dtiles/test/nexus-fixture.js` (a four-node DAG with a node shared by two parents and two
textures) and over the head of the real gargoyle (`test/fixtures/gargo-head.nxz`, 37 KB: header, tables and node
0, decoded from Corto to 3 882 vertices and 7 760 triangles); the statistics of the DAG; truncated and foreign
files; the two tree mappings and the fallback to paths for a DAG that is not layered; a textured node's GLB (one
primitive per texture, images embedded, v flipped) and an untextured one's colours; the live route on a host that
answers `Range` (the tileset from two reads, tiles by node range, a texture read once for several nodes, `dag=`
and `ge=`), on a local file, on a missing file and on a `DEEPZOOM` file; and the offline converter by levels and
by paths.
