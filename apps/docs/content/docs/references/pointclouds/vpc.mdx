## What it is

A `.vpc` is the point-cloud counterpart of a GDAL VRT: one small JSON file that makes a folder of tiles behave
as a single dataset. QGIS loads it as one layer, `pdal_wrench` takes it as input (`build_vpc` writes one), and
PDAL reads it with `readers.stac`.

The file is a **STAC API ItemCollection**: a GeoJSON `FeatureCollection` whose features are STAC items using
the `pointcloud` and `projection` extensions. Not a STAC *Collection*: everything is in the one file.

| Where | What |
|---|---|
| `assets.data.href` | the point cloud file: relative to the `.vpc`, an absolute URL, or a local path. LAS, LAZ, COPC or EPT |
| `properties["proj:bbox"]` | its extent in its **own CRS**, 3D recommended: `[xmin, ymin, zmin, xmax, ymax, zmax]` |
| `proj:wkt2` / `proj:epsg` / `proj:projjson` | that CRS. Each item may have its own; one CRS per VPC is recommended |
| `bbox`, `geometry` | the same extent in WGS 84, which GeoJSON requires. `proj:bbox` wins when present |
| `pc:count`, `pc:type`, `pc:encoding` | point count, kind of capture, encoding |
| `pc:statistics`, `pc:schemas` | optional per-attribute statistics and dimensions |
| `assets.overview` (role `overview`) | optional: a thinned COPC of the **whole** set, shared by every item, or one of several overview tiles |

## How it is served: a mosaic of COPC streams

```
GET /stream/tileset.json?format=vpc&url=<https://….vpc>      # format is detected from .vpc, .vpc.gz and .gridvpc.json[.gz]
GET /aggregate/tileset.json?vpc=<https://….vpc>               # the same mosaic, with /aggregate's own defaults
GET /aggregate/index.json?vpc=<https://….vpc>                 # one row per streamed item
    [&nest=geodetic|mercator|flat] [&bv=…] [&cut=auto|<depth>|0] [&cache=none|hierarchy] [&prefetch=N] [&sniff=auto|all|0] [&ttl=<s>]
```

A `.vpc.gz` is read as is: the gzip magic is checked, not the name or the Content-Type, so a static host that
serves it as `application/gzip` works. A country is 10 000 items and more, 11 MB of JSON that gzip takes to 1 MB.

A VPC has no tiles of its own, so there is no range adapter for it. Each COPC file it lists already streams as
its own tileset (`/stream/tileset.json?format=copc&url=<item>`), and [`/aggregate`](/docs/guide/meta-tilesets)
already builds one tileset out of many. So the `.vpc` is parsed into the manifest `/aggregate` reads
(`packages/tile-server/vpc-live.js`), and the answer is a mosaic whose leaves reference those COPC streams.

**The root is built from the `.vpc` alone.** Each leaf's bounding sphere comes from its item's `proj:bbox`,
reprojected to ECEF with the same proj4 definitions the COPC stream uses for the file, so `/aggregate` gets
its bounds baked (`childRootsBaked` = the item count, `childRootsFetched` = 0 in `asset.extras.build`). A
client opens a COPC file only when it refines into that leaf.

Measured on this machine, server on localhost:

| AHN5 Amsterdam, [HPC-DAT/copc-dataset](https://github.com/HPC-DAT/copc-dataset) (227 M points) | 9 | 6.5 KB | 0.55 s, 0.43 s fetching | 3 groups, depth 2 |
| Dublin City 2015, self-made (1.42 G points) | 35 | 22.9 KB | 70 ms | 7 groups, depth 4 |

| Luxembourg 2019, **all 10 906 tiles**, self-made (80.4 G points, a 1.00 MB `.vpc.gz`, 11.6 MB inflated) | 10 906 | **105 KB** cut; 6.87 MB inline (`&cut=0`) | 420 ms cold, 157 ms warm | 1 060 groups, depth 8, 3 at the root; 72 external subtrees at the root |
| IGN LiDAR HD, Paris 100 km block, self-made (127 G points, a 0.52 MB `.vpc.gz`) | 5 712 | **94 KB** cut; 3.54 MB inline | 315 ms cold, 96 ms warm | 555 groups, depth 6; 104 external subtrees |

In all of them, no COPC file was opened to build the root. Past 1 024 items the mosaic is **cut** into external
tilesets every four group levels, the root holding only the top of the tree: why, and the numbers at 10 000,
100 000 and 337 206 items, are in [the meta-tilesets guide](/docs/guide/meta-tilesets#tens-of-thousands-of-children-the-depth-cut).
From the root of Luxembourg to a leaf's first points: root 157 ms, subtree 12 ms, the leaf's COPC `tileset.json`
714 ms (header and hierarchy from S3), its 440 KB root tile 1.05 s; four requests, 1.9 s.

### A VPC of VPCs: the hierarchy past a few thousand items

The cut keeps the *tileset* small, but the server still parses the whole `.vpc` before answering: all of
France is 337 206 items, 557 MB of JSON (29 MB gzipped) — more than one JavaScript string holds, so the
writer streams the features out and `vpc-split` scans them in — and whoever else opens the file (QGIS, PDAL)
parses every item before showing the first. So past a few thousand items the VPC itself is made
hierarchical, the way Potree's hierarchy is cut into pages: **a root VPC whose items stand for child VPC
files**, each child under an item count and a JSON size.

```bash
node scripts/vpc-split.mjs country.vpc.gz -o out/country.vpc.gz [--max-items 2048] [--max-bytes 2000000] [--flat]
#  → out/country.vpc.gz                  the root: one item per child, the union of the child's extents
#    out/country/<quadkey>.vpc.gz         the children, the items unchanged
#  --flat: the children beside the root as out/country.<quadkey>.vpc.gz, for a host without folders
```

**How the quadtree is built.** Two limits, and a cell is cut until it meets both:

| Limit | Default | Flag |
|---|---:|---|
| items in one VPC file | **2 048** | `--max-items` |
| JSON of one VPC file, before gzip | **2 MB** (2 000 000 bytes) | `--max-bytes` (`5000000` for 5 MB pages) |

1. Every item gets a point: the centre of its WGS 84 `bbox` (or of its `geometry`).
2. Starting from all the items as one cell: if the cell has at most 2 048 items **and** their JSON is at most
   2 MB, it is a leaf and becomes one child file. Otherwise it is cut in four at the midpoint of its items'
   centres (quadrant 0 south-west, 1 south-east, 2 north-west, 3 north-east), and each non-empty quadrant is
   cut again the same way. A child's name is its **quadkey**, one digit per cut: `france-lidarhd.1203.vpc.gz`
   is the north-east quarter of the south-west quarter of the north-west quarter of the south-east quarter.
   The tree is as deep as the densest corner needs and no deeper: France's leaves are 3 to 5 digits.
3. The root is then written. It holds one item per leaf file when those items fit the same two limits
   themselves (563 summary items are 1 MB of JSON: they do), so a reader hops once from the root to any
   child. Only when they would not fit does a level of intermediate VPC files appear between the two, each
   listing its own quadrants (France at `--max-items 8` is such a tree).

The byte limit is what bites when items are heavy: an IGN item carries its own Lambert-93 WKT, about 1.65 KB
of JSON, so 2 MB is reached at 1 200 items, before the 2 048. France's 563 children hold 9 to 1 200 items
(median 525) and none is over 1.98 MB of JSON. A child is named in the root in both STAC forms at once:

1. **an item** whose `assets.data.href` is the child file, `pc:type: "vpc"`, `pc:encoding:
   "application/geo+json"`, `vpc:items` the number of point cloud files below it, `pc:count` their sum,
   `bbox` / `geometry` / `proj:bbox` the union of its items (the native box only when the items share one
   CRS). This form carries the bounds, so a root is served without opening a child.
2. **a root-level `links` entry** of `rel: "child"`, which STAC crawlers follow. A link carries no bounds, so
   a child named only by a link is placed by reading its mosaic root (`boundsFrom.probe`); one an item
   already names adds nothing.

Each child file carries a `rel: "parent"` link back. A nested item becomes a `format: vpc` entry of the mosaic
whose leaf content is this server's own mosaic of that child, `/stream/tileset.json?format=vpc&url=<child>`:
the root mosaic is built from the root file alone, and a child file is read only when a client refines into its
cell, where it is served as any VPC, cut again every four group levels when it holds more than 1 024 items.
The tree a client walks is then root → (child VPC → subtree)… → COPC root → tiles, each page a few tens of KB.
`asset.extras.vpc.nested` counts the nested entries; `index.json` lists them as `vpc` rows. An item with
no extension but `pc:type: "vpc"` (or an asset typed as one) is taken for a nested VPC as well.

A PDAL `readers.stac` that cannot read a `.vpc` asset filters the items out on `pc:type`; QGIS draws the
extents and fails only the sub-index it tries to open. What the split did to the four country sets, and the walk
from the root to the first points of a leaf, measured on this machine with the files served from
`/samples/` on localhost (they have since moved to a GitHub release, [see below](#where-the-sets-are-kept)):

|---|---:|---:|---|---|
| IGN LiDAR HD, all of France | 337 206 | 563 items, 60 KB gzipped (993 KB JSON); served 293 KB in 669 ms | 563 files of 9–1 200 items (median 525), 1.98 MB of JSON at most, 30 MB gzipped in all, quadtree 5 deep | 669 ms · 19 KB in 326 ms (1 054 items, cut: 30 externals) · 34 KB in 29 ms · 0.8 s · 1.25 MB in 1.3 s |
| swissSURFACE3D | 15 643 | 27 items, 4 KB (47 KB JSON); 16 KB in 257 ms | 27 files of 22–1 033 items, 1.5 MB in all, quadtree 3 deep | 257 ms · 317 KB in 208 ms (498 items, no cut) · 0.9 s · 1.09 MB in 0.9 s |

Against the depth cut alone on the same 337 206 items (measured on the estimated build, 225 MB without each
item's WKT: a 22 KB root, but 12.7 s cold to parse the `.vpc` and 2.6 s warm; the final 557 MB one no longer
fits a JavaScript string at all), the split root is a 60 KB file that answers in 0.7 s with nothing else
read, and a child of 1 000 items costs what Luxembourg's first 1 000 did. What a client waits for is still
the point cloud: the COPC root (header and hierarchy from S3) and its first tile are a second or two each
(timings from one morning; the same walk the evening before saw 5–11 s per S3 read), the three index hops
together about a second.

### What a client sees, from the whole country down

The mosaic's groups have no content of their own: only a leaf, a COPC file's own stream, draws points. So:

- **Seen whole, a country shows nothing.** The client reads the root (23 to 293 KB) and the few subtrees its
  screen-space error asks for, all of them JSON. No COPC file is opened: 337 206 tiles cost no request.
- **A tile opens when the group above it refines.** A group's geometric error is twice its largest child's,
  and a 1 km leaf declares 1 732 m (the diagonal of its octree cube), so the group over four tiles has 3 464 m.
  At the usual 16 px threshold on a 1 000 px, 60° viewport that group refines within about **190 km** of the
  camera, and each tile under it then reads its COPC root: one `tileset.json` (header and hierarchy, two range
  reads on the source) and one root node, 0.4 to 1.3 MB.
- **From there on it is the file's own octree**, refined by its own errors (a 1 km tile's root node declares
  about 7 m).

190 km is early: a camera that high over dense coverage has tens of thousands of tiles in view, and their
roots are requested as fast as the renderer's queue lets them. It is correct, and it is the cost of a mosaic
without an overview; the fix is the overview asset as the groups' content (below), not yet built. Until then,
open a country zoomed in, or raise the renderer's error threshold while flying in. (The distance is computed
from the errors the server writes, not observed in a browser.)

### Which items are streamed

Only **COPC** items. A plain LAS or LAZ file has no levels of detail to map onto tiles, the reason the
converter refuses one as well. The rest are skipped, never silently:

| The href | What happens |
|---|---|
| ends in `.copc.laz` | streamed. No request |
| ends in `.laz` | may be a COPC (it is a valid LAZ 1.4, and nothing forces the double extension). One 589-byte range read tells: the `copc` info VLR sits right after the LAS header |
| ends in `.las` | skipped: *plain LAS* |
| `ept.json` | skipped: EPT is not supported |
| a drive letter, a UNC path, `file://`, `s3://` | skipped: *local path* or *unsupported scheme*. The server reads sources over HTTP |

`&sniff=auto` (default) reads the first 16 `.laz` items; if none is a COPC, the others are taken for plain LAZ
unread, so a VPC of 10 000 plain tiles does not cost 10 000 requests to say so. `&sniff=all` reads every one,
`&sniff=0` none.

The count and the reasons are in `asset.extras.vpc` (`items`, `streamed`, `skipped`, `skippedReasons`, the
first 20 `skippedItems`, `sniffed`, `boundsFrom`, `points`), in the response headers `X-VPC-Items`,
`X-VPC-Streamed`, `X-VPC-Skipped`, `X-VPC-Skipped-Reasons`, and in the server log. A VPC with no COPC item at
all answers **422** with the same report and what to do about it. Example, 9 AHN5 COPC items mixed with five
plain `.laz` and one `.las`: `X-VPC-Streamed: 9`, `X-VPC-Skipped: 6`,
`1 plain LAS (no levels of detail); 5 plain LAZ (no levels of detail)`, 5 files read to tell.

### Where each item is placed

1. `proj:bbox` in the item's own CRS, tried as `proj:wkt2`, then `proj:projjson`, then `proj:epsg` /
   `proj:code`. The WKT first: PDAL copies it from the file, and the COPC stream places the file from that
   same text. A compound CRS (WKT1 `COMPD_CS`, WKT2 `COMPOUNDCRS`, PROJJSON `CompoundCRS`) is read through its
   horizontal part; heights are taken as they are. A 2D `proj:bbox` takes its heights from a 3D `bbox`.
2. the WGS 84 `bbox`, when there is no native box or proj4 cannot read the CRS;
3. the extent of `geometry`;
4. nothing usable: the item has no baked bounds, and `/aggregate` reads that one file's root, as it does for
   any child without them (`boundsFrom.probe` counts these).

Items of one VPC may each have their own CRS. Past 20 km a box is sampled 5 × 5 on its top and bottom faces
and the dip of the ellipsoid between samples is added: a box over a country is not flat.

The leaf's sphere encloses the **points** (the header's tight box); the COPC stream's own root encloses the
octree **cube**, which is larger, and not always centred on the points. Compared on real files:

| File | Centre distance | Leaf radius / child-root radius | Geometric error, leaf / child |
|---|---:|---:|---:|
| AHN5 `124000_484000` (PDAL cube, centred) | 0.00 m | 707.4 / 866.0 = 0.82 | 1732.19 / 1732.0 |
| Dublin `T_316500_233500` | 0.85 m | 432.5 / 433.0 = 1.00 | 865.83 / 866.0 |
| Dublin `T_317000_234000` (a partial tile) | 143 m | 369.3 / 433.0 = 0.85 | 865.83 / 866.0 |
| Luxembourg `100500_88500` (a height outlier: the cube is 2.2 km) | 1 233 m | 1176.5 / 1943.6 = 0.61 | 3887.16 / 3887.2 |

The geometric error of a leaf is the diagonal of the cube a COPC of that extent has (longest side × √3), which
is what the child declares for its own root: the two refine in order.

**A file without a CRS of its own.** A COPC stream takes its CRS from the file. Some files carry none (flai's
mirror), and the COPC files QGIS itself writes keep it in a private `qgis` record. The item's EPSG code, from
`proj:epsg` or from the identifier inside its WKT, therefore rides on each leaf as `&crs=EPSG:<n>`, which a
file's own CRS always overrides. A code this server does not know is registered from the item's own WKT when
the VPC is read, for the life of the process.

### The overview asset

Not used as root content, and reported instead: `asset.extras.vpc.overviews` lists each overview with a ready
`/stream/tileset.json?format=copc&url=…` URL.

The natural design, the overview as the root's content with `refine: REPLACE` over the per-file leaves, is
not valid 3D Tiles: a tile whose content is an external tileset may not have children. The workaround is to
put one GLB of the overview (its root node) on the root. That needs the overview's header read before the
root can answer, a root transform that every leaf then has to undo, and it shows one level of a file that has
a whole pyramid. Without it the mosaic's groups are empty, so from far away every leaf in view opens its
COPC root: for the 10 906 Luxembourg tiles seen whole, 10 906 small requests. That is the cost of leaving the
overview out, and the next thing to build here.

## Writing one without PDAL

`scripts/copc-to-vpc.mjs` writes a VPC over COPC files that are already online: one 2 KB range read per file
(the 375-byte LAS 1.4 header, the `copc` VLR behind it, the laszip VLR and a WKT VLR when there is one; a file
whose VLRs run past 2 KB is read again with the 64 KB COPC reader), no statistics. `-o x.vpc.gz` writes it
gzipped. `packages/tile-server/samples/dublin-city-2015.vpc` was made with it (35 tiles of NYU's 2015 Dublin
scan, CC BY 4.0, from flai's public mirror; 4.3 s):

```bash
node scripts/copc-to-vpc.mjs --s3 https://open-lidar-data.s3.eu-central-1.amazonaws.com \
  --prefix data/IE/NYU_EDU/Dublin_City_2015/copc/ --crs EPSG:29902 \
  --overview https://open-lidar-data.s3.eu-central-1.amazonaws.com/data/IE/NYU_EDU/Dublin_City_2015/overview/overview.copc.laz \
  -o dublin-city-2015.vpc
```

Three ways to know where a tile is and how many points it holds, from the exact to the free:

| Mode | Reads | Gives | When |
|---|---|---|---|
| default | one 2 KB header per file | exact extent, count, WKT, date | always right; 337 206 files are about 70 minutes of reads at 16–32 in flight, over three runs resumed from `--cache` |
| `--estimate <grid>` (`ign-lidarhd`, `swisstopo`) | `--calibrate N` headers (500) drawn at random | the footprint from the tile **name**, `pc:count` from the file **size** the `--s3` listing gives through a fitted bytes-per-point ratio (printed), heights from the nearest calibrated tiles; items marked `"3dtiled:estimated": ["pc:count", "z"]` | a country in two minutes; a later run without it replaces the estimates |
| `--grid <grid> --extent x0,y0,x1,y1 --url <template>` | nothing | every cell of the extent (km) as an item, `{x}` / `{y}` filled into the template, `--points N` each, `--z lo,hi`; marked `["pc:count", "z", "exists"]` | no listing at all. A cell with no file 404s when a client reaches it, which `/aggregate` reports as a failed child and the viewer skips. Fits a grid whose file name is a function of the cell alone; where a name has a second part (IGN's `_C_` / `_O_`), or the extent has holes worth not asking for, write a [grid VPC](#a-grid-vpc-the-campaigns-grid-said-once) from a listing instead |

`--cache headers.ndjson` keeps every header read as it lands and skips it on the next run, so a run that is
killed or a link that drops resumes where it was (a WKT is written once, the files that share it point at it);
`--listing keys.tsv` does the same for the bucket listing; `--concurrency N` (16) sets the reads in flight.

  at 32 in flight; split into 147 children (9.9 MB gzipped in all).
- **`usgs-3dep-fairbanks-2017.vpc.gz`** (release): a USGS 3DEP project as NOAA's Digital Coast keeps it in COPC on a public
  bucket (`noaa-nos-coastal-lidar-pds.s3.amazonaws.com/laz/geoid12b/8663/`, dataset 8663: Fairbanks North Star
  Borough, Alaska, 2017, QL1 and QL2), 7 471 tiles, 63.0 G points, heights 34–1 889 m, `NAD83(2011) / UTM zone 6N`
  (EPSG 6335) with NAVD88 heights. 13.3 MB of JSON, 0.81 MB gzipped, 230 s; split into 15 children. USGS's own
  3DEP tiles are EPT on `usgs-lidar-public` (not COPC) and COPC behind Planetary Computer's signed URLs, neither
  of which a static VPC can point at; NOAA's copies of the 3DEP projects on the coast are plain COPC.

### IGN LiDAR HD: where the tiles are, and in what form

IGN's programme covers metropolitan France in 1 km tiles of classified LAZ 1.4 (*nuages de points classés*),
under the Licence Ouverte 2.0. Found on 2026-11-10:

- **The index** is the WFS layer `IGNF_LIDAR-HD_TA:nuage-dalle` on `data.geopf.fr/private/wfs` (with
  `nuage-bloc`, `mnt-dalle`, `mns-dalle`, `mnh-dalle` for the derived products), one feature per tile with a
  `name` (`LHD_FXX_<x km>_<y km>_PTS_C_LAMB93_IGN69`) and a download `url`. It is what the download portal
  (`diffusion-lidarhd.ign.fr`, now `cartes.gouv.fr/telechargement/IGNF_NUAGES-DE-POINTS-LIDAR-HD`) reads, with the
  key `interface_catalogue`; from outside the portal every one of these offerings answers 403, and the public
  WFS lists only `IGNF_LIDAR-HD_METADONNEE`. So IGN's own tile URLs, and whether IGN's own files are COPC, could
  not be checked from here.
- **A COPC distribution exists**: flai's `open-lidar-data` bucket mirrors 337 206 tiles as `.copc.laz` under
  `data/FR/IGN/Lidar_2021/copc/`, keeping IGN's names (258 474 `_PTS_C_`, 78 716 `_PTS_O_`, never both for one
  square, and 16 older `LHD_C_LA93-IGN69_<x>-<y>_2021` names), with a 15 GB `overview.copc.laz`. Every one of
  the 5 712 read has the `copc` VLR first. This is the set the Paris block comes from.
- **All of France is built**, twice over. First from the bucket listing alone (`--estimate ign-lidarhd`,
  109 s): the footprint from the tile name, the count from the file size through a bytes-per-point ratio fitted
  on 3 000 header reads (5.609 B/point; median 5.593, p10 4.25, p90 6.60; a tile's count is within 10.4 % of
  the truth at the median and 28 % at the 90th percentile), the heights from the nearest calibrated tiles.
  Then from every header (10 071 G points against the 10 043 G estimated, the sum 0.3 % off; 557 MB of JSON,
  29.4 MB gzipped, about 70 minutes of reads), the set that is published, split in 563 child files.
- **The name is the place, and the grid is enough to build the set.** `LHD_FXX_<x>_<y>` is the north-west
  corner of the square kilometre in Lambert-93 km: nothing else is needed to place a tile, and every header
  read agreed with its name. What a name does not say is which squares exist (the programme is in progress,
  and the bounding box of France is 1.1 M squares for 337 206 tiles: the rest are sea, neighbours and blocks
  not yet delivered, where a 404 is simply true) and, on flai's mirror, whether a square is called
  `_PTS_C_` (258 474) or `_PTS_O_` (78 716; never both for one square). An earlier version of this page
  concluded from the second point that a grid template "404s on a quarter of its cells". That was a wrong
  conclusion from a right observation: a template with **one** fixed name misses the `_O_` squares, but the
  remedy is to write down, per square, that it exists and which of the two it is. That is one character per
  square, and it is the [grid VPC](#a-grid-vpc-the-campaigns-grid-said-once) below: all of France in 9.5 KB.

### A grid VPC: the campaign's grid, said once

A STAC VPC over a national campaign repeats per tile what the grid already says: a URL that differs by two
numbers, a polygon, two boxes, a WKT. For France that is 557 MB of JSON, 30 MB gzipped in 563 files, after
70 minutes of header reads. The **grid VPC** (`packages/tile-server/vpc-grid.js`, `"type": "3dtiled:GridVPC"`,
`.gridvpc.json[.gz]`) says it once:

```json
{
  "type": "3dtiled:GridVPC", "version": 1,
  "title": "IGN LiDAR HD, all of France", "license": "Licence Ouverte 2.0 (Etalab)",
  "crs": "EPSG:2154", "unit": 1000, "cell": 1000, "anchor": "nw",
  "url": "https://open-lidar-data.s3.eu-central-1.amazonaws.com/data/FR/IGN/Lidar_2021/copc/LHD_FXX_{x}_{y}_PTS_{v}_LAMB93_IGN69.copc.laz",
  "pad": 4, "variants": ["C", "O"],
  "x0": 186, "y0": 6047, "width": 1057, "height": 1065,
  "zRange": [-30, 2871], "pointsPerCell": 29866661,
  "rows": ["...........0000011100....", "…"],
  "z": { "min": [31, 30, "…"], "max": [121, 99, "…"] },
  "points": { "unit": 100000, "counts": [213, 90, "…"] },
  "extra": [{ "url": "https://…/LHD_C_LA93-IGN69_0932-6503_2021.copc.laz", "bbox": [932000, 6502000, 279.19, 932999.99, 6502999.99, 576.42], "points": 33377564 }]
}
```

| Field | Meaning |
|---|---|
| `crs`, `unit`, `cell`, `anchor` | the grid: its CRS, the metres one unit of an index stands for, the side of a tile, and the corner a name gives (`nw` for IGN, `sw` for swisstopo) |
| `url`, `pad`, `variants` | the name of a square: `{x}` and `{y}` zero-padded to `pad`, `{v}` one of the variants. Absolute, or relative to the descriptor |
| `x0`, `y0`, `rows` | **the availability**: one string per row from `y0` upwards, one character per square from `x0`; `.` no tile, else the index of its variant |
| `z`, `points` | optional, per present square in row order: its heights in metres (clamped to −1 000…9 000: ten IGN headers claim ±1 000 km) and its count in units of `points.unit` |
| `zRange`, `pointsPerCell` | what a square is given when `z` / `points` are left out |
| `extra` | files that are not of the grid (IGN's 16 older names), each with its own box in `crs` |

The server expands it in memory into the entries a STAC VPC gives (`asset.extras.vpc.boundsFrom` says
`grid`), and the mosaic is built, cut and served as any other. Two files for all of France:

| | Size | A square's box | Use |
|---|---:|---|---|
| `france-lidarhd.gridvpc.json.gz` (repository) | **9.5 KB** | the country's range, −30 to 2 871 m, for every square: a box 2.9 km tall, so a tile opens from about three times further than it should, and a summit above the range can be culled | the availability alone; no header was needed to write it, a bucket listing is enough |
| `france-lidarhd-stats.gridvpc.json.gz` (release) | 1.5 MB | each tile's own heights from its header, to the metre; counts to 100 000 points | the library's default for France |

```bash
node scripts/vpc-to-grid.mjs france.vpc.gz --grid ign-lidarhd \
  --url 'https://…/copc/LHD_FXX_{x}_{y}_PTS_{v}_LAMB93_IGN69.copc.laz' -o france.gridvpc.json.gz [--no-stats]
```

reads a flat or split VPC, places each item from its **name** through the grid (`ign-lidarhd`, `swisstopo`),
takes `{v}` from what the template leaves open, and keeps under `extra` any file whose name is not of the
grid. Measured, all of France served from the 9.5 KB file by a local server:

| | Grid VPC | Split STAC VPC |
|---|---|---|
| What is fetched for the root | 9.5 KB (or 1.5 MB) | 60 KB |
| First root, cold | about 30 s: 337 206 boxes projected (4.5 s), the selection keyed (10 s), the tree built (4 s) | 0.7 s: only the 563 summaries are read |
| Root again | 0.1 s | 0.1 s |
| A subtree (`&cell=`) | 0.15 s, 270 KB | a child VPC, 0.3 s, then its subtree |
| Root `tileset.json` | 23 KB, 34 external subtrees | 293 KB |
| Opens in QGIS / PDAL | no | yes |
| Files to host | 1 | 564 |

So the grid costs one slow first request per server per day, kept in memory after that, against 30 MB less to
host and nothing to read to build it. The split STAC VPC stays for what reads STAC.

Not covered: IGN's own distribution. Its tile index is the WFS layer `IGNF_LIDAR-HD_TA:nuage-dalle`, which
answers 403 outside IGN's portal (tried again on 2026-11-12 with the portal's key and referer), so the
availability here is flai's listing of 2026-11-10, not IGN's, and it ages as the programme delivers blocks:
rebuild from a fresh listing. What `_O_` stands for against `_C_` is not stated anywhere this page could cite.

`scripts/vpc-to-manifest.mjs <file.vpc | url> -o set.json` goes the other way: a VPC to an `/aggregate` set
manifest with baked bounds, to edit, to keep as a named set, or to `POST /aggregate/set`.

## Not supported

- **Plain LAS/LAZ and EPT items**: skipped, as above.
- **Local paths.** The `.vpc` and its files are read over HTTP. A `.vpc` written with absolute local paths
  has to be rewritten; one with relative paths works once the folder is published.
- **Offline conversion.** `3dtiled <x.vpc> <outDir>` is refused with a message: convert the COPC files one by
  one, or serve the VPC (`3dtiled serve <url>.vpc`).
- **`&attributes=`, `&colors=`, `&transform=`, `&tiling=`** are not passed on to the COPC leaves.
- **Tiled overviews, `pc:statistics`, `proj:geometry`**: read by nothing here.
- **Vertical datums**: heights are placed as ellipsoidal, as everywhere in this toolbox.
