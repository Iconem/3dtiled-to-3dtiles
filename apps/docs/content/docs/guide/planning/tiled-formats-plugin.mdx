Plan of 2026-11-19, replacing the draft of 2026-11-16. **Not started**: this page is the plan only. The roadmap
item is on the [future work](/docs/guide/todo-future-work) page.

## The idea

Today a tiled source reaches the renderer through the tile server:

```
COPC / Nexus / I3S / …  →  tile server (/stream)  →  3D Tiles (tileset.json + GLB)  →  3DTilesRendererJS
```

The server does three things per source: reads the source's own hierarchy, turns it into a 3D Tiles tree, and
decodes one node into one GLB on request. All three are JavaScript. The plan is to run them **inside the renderer**,
as plugins:

```
COPC / Nexus / I3S / …  →  3DTilesRendererJS + a plugin (range requests, decode in Web Workers)
```

## What changed since the draft

Two things were checked in the installed packages on 2026-11-19, and both shrink the project.

- **Potree is upstream.** `PotreePlugin` of 3DTilesRendererJS 0.5.4 reads Potree **1.x and 2.0**, with the adaptive
  point size and eye-dome lighting of `PointCloudEffectsPlugin`. It refuses two cases by name: a 2.0 cloud whose
  encoding is not `DEFAULT` (Brotli), and a 1.x cloud whose nodes are LAS or LAZ files. It decodes on the main
  thread. So Potree is no longer a plugin to write: at most the two refused cases, offered upstream.
- **Splats have their own streaming.** Gaussian Splat Lite 1.8.1, the renderer the viewer's splat plugin draws
  with, streams RAD, streamed SOG and LCC2 itself (`RadStreamScheduler`, `SogStreamScheduler`,
  `Lcc2StreamScheduler`). A tiles plugin for those formats would duplicate it. What is left for splats is LCC
  version 1, and setting a scene on the globe, which is glue in the viewer, not a reader.

That leaves **COPC and VPC**, which nothing in the browser reads into a tiles renderer today, and the four mesh
formats: **Nexus, 3MX, I3S, OSGB**.

## What it gives, what it costs

| | Tile server (today) | Plugin in the browser |
|---|---|---|
| Hosting | a Node process somewhere | none: the source on any static host or bucket |
| Works offline, in any three.js app | no | yes |
| Source requirements | the server must reach it | CORS and HTTP range requests from the browser |
| Decode CPU | the server's cores, shared by all viewers | each viewer's own cores (Web Workers) |
| Cache | shared: one decode serves everyone (`cache=full`) | per browser |
| Other clients (CesiumJS, Unreal, QGIS, Blender) | all of them: they receive plain 3D Tiles | 3DTilesRendererJS only |
| Transforms, export, aggregation | yes | no |
| Crop and extract | yes | yes, already: the [browser extract](/docs/guide/planning/browser-crop-extract) walks any tileset |

The plugins do not replace the server. They cover "I have a COPC on a bucket and a three.js page" with nothing to
run. The server stays the answer for every other client and for anything that writes.

## The hooks a plugin implements

Read off `TilesRendererBase.js`, `PotreePlugin.js` and `QuantizedMeshPlugin.js` of 3DTilesRendererJS 0.5.4. These
are the ones a format plugin needs; both upstream plugins use exactly this set.

| Hook | What the plugin does there |
|---|---|
| `init(tiles)`, `dispose()` | keep the renderer, create the reader, route its requests through `tiles.invokeOnePlugin(p => p.fetchData…)` so that auth and URL plugins still apply |
| `loadRootTileset()` | open the source (header, first hierarchy page), return a synthetic tileset whose root has a made-up content URI (`r.potree`), then `tiles.preprocessTileset(tileset, baseUrl)` |
| `fetchData(uri, options)` | for its own URIs only (recognised by extension): the node's bytes, by range request; `null` for anything else |
| `parseToMesh(buffer, tile, extension, uri)` | the node's bytes to a three.js object, and **push the node's children into `tile.children`** as plain tile objects: the tree grows as tiles load, the hierarchy is never read whole |
| `disposeTile(tile)` | drop the children it pushed (and take them off `tiles.processNodeQueue`), free what it built |
| `setTileActive(tile, active)` | only for the adaptive point size: mark the active set dirty, rebuilt on `update-after` |
| `getAttributions(target)` | the source's credit |

Not needed: `preprocessNode`, `parseTile`, `calculateTileViewError`, `raycastTile`.

A point-cloud plugin **extends `PointCloudEffectsPlugin`** as `PotreePlugin` does, so point shape, size clamping,
eye-dome lighting and the adaptive size come with it. That needs the node's octree key on each tile, which COPC has
(`depth-x-y-z`). The adaptive size per tile of
[3DTilesRendererJS#1792](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1792) is not released yet: until it
is, the plugin builds on the copy vendored in the Potree lab.

## What ties each reader to Node

Measured on 2026-11-19 by listing the Node imports and `Buffer` uses of each reader. "Offline only" means the
import is in the converter's file-writing entry point, which a plugin does not use.

| Format | Reader here | Node imports in the reader | To do for a browser |
|---|---|---|---|
| **COPC** | `tile-server/copc-live.js`, `core/octree.js` | none; 6 `Buffer` uses | `Buffer` to `Uint8Array`; `copc` and `laz-perf` (WebAssembly) and `proj4` already run in browsers |
| **VPC, grid VPC** | `vpc-live.js`, `vpc-grid.js` | `path`, `url`, `zlib` in `vpc-live.js`; none in `vpc-grid.js` | a tree of COPCs: URL handling without `path`, gzip through `DecompressionStream` |
| **Nexus** | `nexus-reader.js`, `nexus-glb.js`, `nexus-tileset.js` | none; 5 `Buffer` uses | `Buffer` to `Uint8Array`. The Corto decoder is plain JavaScript |
| **3MX** | `threemx-live.js`, `ctm-decode.js` | `fs`, `path`, `url` in `ctm-decode.js` | how the vendored OpenCTM decoder is loaded: an import instead of a file read |
| **I3S, SLPK** | `i3sParse.js`, `lepccDecode.js`, `glbBuild.js` | `fs/promises`, `path`, `zlib` in `i3sParse.js` | gzip through `DecompressionStream`; an SLPK by range needs the zip directory reader (`remote-zip.js`) |
| **OSGB** | `osgb-reader.js`, `osgb-image.js` | `zlib` in `osgb-reader.js` | inflate through `DecompressionStream`; images decode natively (`createImageBitmap`) instead of `pngjs` and `jpeg-js` |

Range reads already go through `fetch` with a `Range` header, which browsers do the same way. The shared extractor
(`core/extract-core.js`) made the same move in November: no Node imports, `Uint8Array` throughout, one module for
the server and a worker. It is the model.

## Design

**One set of readers, two front ends.** A reader takes a *source* (an object with `range(offset, length)` and
`whole()`), and offers:

- `open(source)`: the header and the part of the hierarchy needed first;
- `children(node)`: the next nodes, read lazily (COPC hierarchy pages, Nexus node index, I3S node pages);
- `decode(node, bytes)`: **typed arrays** (positions, colours, extra attributes, indices, texture bytes), not a GLB.

The server keeps writing a GLB from those arrays. The plugin builds a `BufferGeometry` from them directly: writing
a GLB to parse it again in the same process would be wasted work. `copcViewGlb`, `potreeDataGlb` and `mesh-tile.js`
are already cut this way; the rest need the same cut.

**Workers.** A node is fetched by range and decoded in a Web Worker, as upstream's Potree plugin does not yet do.
The task shape is the one tile workers use on the server (`{ module, fn, args }`), so the task modules are shared.

**Placement.** A source in a projected CRS is placed with `proj4`, as on the server: a root transform for small
extents, the per-tile sampled placement (documented on the [meta-tilesets](/docs/guide/meta-tilesets) page) for
large ones. A local source takes the five numbers of `core/placement.js` (`lon`, `lat`, `alt`, `heading`, `scale`),
the same the server's `/stream` takes.

**Where it lives.** A package of this repo, `packages/tiles-plugins`, one entry point per format so that a COPC
viewer never downloads the OpenCTM decoder:

```
packages/tiles-plugins/
  source.js              range(offset, length), whole(): over fetch, with the renderer's fetchOptions
  copc/CopcPlugin.js     extends PointCloudEffectsPlugin; reader: core/octree.js + the COPC part of copc-live.js
  copc/VpcPlugin.js      a VPC as a tree of CopcPlugin roots
  nexus/NexusPlugin.js   reader: nexus-reader.js
  threemx/…  i3s/…  osgb/…
  workers/decode.worker.js
```

```js
import { TilesRenderer } from '3d-tiles-renderer';
import { CopcPlugin } from '3dtiled-tiles-plugins/copc';

const tiles = new TilesRenderer();
tiles.registerPlugin(new CopcPlugin({ url: 'https://bucket.example/scan.copc.laz', crs: 'EPSG:2154' }));
```

Published under our name. Offering any of it upstream is a later conversation and only with the maintainer's
interest; nothing is posted without a go.

## Phases

Sizes are rough, in working days for one person who knows the readers.

| Phase | What | Done when | Size |
|---|---|---|---|
| **0. Spike** | COPC only, in the Potree lab as a new mode next to the server one. Reader called as is, bundled for the browser, decode on the main thread. | Autzen renders from its bucket with no server; time to first tile, tiles per second and main-thread stalls written down beside the server path | 2 |
| **1. Source and workers** | the source abstraction, `decode` to typed arrays for COPC, the decode worker; the server moves onto the same reader | every existing COPC test passes on the server; the reader's tests also pass in headless Chrome | 3 |
| **2. COPC and VPC** | `CopcPlugin` on `PointCloudEffectsPlugin`, CRS placement, extra attributes; `VpcPlugin` and the grid VPC | the lab's COPC and VPC presets load in plugin mode, sized and coloured as in server mode | 4 |
| **3. Meshes** | Nexus, then 3MX, I3S (with SLPK), OSGB | each mesh preset loads in plugin mode, same triangle counts as server mode | 2 to 3 each |
| **4. Release** | npm package, a demo page on GitHub Pages per format, the docs below | someone outside loads their own COPC from a README snippet | 2 |
| **5. Upstream** | show it to 3DTilesRendererJS; ask what, if anything, belongs there. Offer the two Potree cases it refuses (Brotli, LAZ nodes) if wanted | a reply | |

**Phase 0, first attempt done on 2026-11-19** (`apps/viewer/src/potree-lab/copcPlugin.js`, lab mode `copc`).
Shorter than planned, because of one observation: a COPC octree has the shape of a Potree one, so the plugin is
upstream's `PotreePlugin` with another loader (about 200 lines), not a plugin written from the hooks. Autzen and
the Namur overview draw from their buckets with no server, with the adaptive size and eye-dome lighting; the
hierarchy stays lazy. Reader: [copc.js](https://github.com/connormanning/copc.js) with laz-perf, which Potree and
Giro3D also use; no faster reader was found, and none was measured. **Still owed by phase 0**: the numbers (time
to first tile, tiles per second, main-thread stalls) beside the server path, on a machine with a GPU.

**Second pass, 2026-11-21**: decoding in workers, the other attributes, and placement on the globe from the CRS
(see the [Potree lab](/docs/guide/potree-lab)). Still owed: the numbers on a machine with a GPU.

**Should Potree and COPC derive from one octree point cloud plugin?** Yes for the plugin, no for the loaders.
Read in 3DTilesRendererJS 0.5.4: `PotreePlugin.js` is format-neutral almost throughout (the octree turned into
tiles, the error halved per level, the bounds, the adaptive point size); what is Potree's in it is one line that
builds the loader and five uses of the literal `potree` extension. The two loaders share no code, so the loader is
an interface, which `CopcLoader` already satisfies: `load(url)` leaving `metadata = { spacing, boundingBox }`,
`hierarchy.get(key)` giving `{ childMask }`, `loadNodeData(key)` and `parsePointData(buffer, key, min, max)`.
What the subclass has to work around today says what an upstream change would need: a hook to supply the loader
(ours replaces it after `init` has built a Potree one), a guard for a node the hierarchy does not hold yet (lazy
hierarchy pages), a hook to give the root a transform and a unit scale, and a name other than `.potree` for the
nodes. It overlaps the active-nodes texture of upstream PR #1792, so it would be proposed after that one. Nothing
has been proposed upstream.

Phase 0 decides whether the rest is worth it: if a COPC from a bucket is not at least as quick to a first view as
through the server on the same machine, the project stops there. Phases 2 and 3 are independent once 1 is done.

**Not in this plan:** Potree (upstream has it), RAD, streamed SOG and LCC2 (the splat renderer has them), LCC
version 1 (parked with its harmonics), writing or converting anything.

## Tests to do

- **Same bytes, both sides.** For a fixed list of nodes per format, the typed arrays decoded in Node and in a
  browser hash the same. This is the test that lets the server and the plugin share readers safely.
- **Reader unit tests** run under `node --test` as today, and once more in headless Chrome.
- **Render checks** with the headless Chrome script: each preset in plugin mode against server mode, same camera,
  point or triangle counts and bounding boxes compared, a screenshot kept.
- **Hosting matrix**: a bucket with and without CORS, with and without range support, behind a CDN that answers
  `200` to a range request. Each failure must give a message that names the cause, as the browser extract's does.
- **Performance**, as ratios against the server path on the same source: time to first tile, tiles per second,
  longest main-thread stall, memory after a fly-through. On a laptop and on a phone.
- **Bundle size** per entry point, with a budget (the LAZ decoder alone is a few hundred kilobytes).
- **Large inputs**: a 200 GB COPC, a country-wide VPC. The hierarchy must stay lazy.
- **Lifecycle**: tiles disposed and reloaded many times, the page left open for an hour, workers terminated.

## Open questions

- **CRS grids.** `proj4` without grid shift files is exact enough for most national grids, not all. Fetching grids
  on demand in a browser is unsolved here.
- **Licences** of what a browser bundle would redistribute: OpenCTM, Corto, the LEPCC port, `laz-perf`.
- **Sources that are folders** (OSGB, 3MX): a browser cannot list a directory, so the entry file must name
  everything. To check per format before phase 3.
- **Mobile memory.** A LAZ chunk decodes to several times its size; node size limits may be needed.
- **How much upstream wants.** A COPC plugin may be welcome there; five formats probably not.

## To decide before starting

1. **Go or no go on phase 0** (two days, ends with numbers).
2. **The adaptive point size**: wait for #1792 to be released, or build on the vendored copy and switch later.
3. **The name and the scope of the package**: `3dtiled-tiles-plugins` under jo-chemla, COPC first, meshes only if
   phase 2 is used by someone.
