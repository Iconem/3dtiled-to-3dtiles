Unchanged, their lists already matched: untwine, PotreeConverter 2, gocesiumtiler, point-tiler, py3dtiles, Obj2Tiles,

- **A bug found on the way.** splat-transform was offered for `.spz`, `.sog`, `.splat` and `.ksplat`, and failed on
  all four: it merges levels of detail from PLY files only. Such an input is now first written out as a PLY.
  `.spz`, `.sog` and `.splat` were run after the fix; these had never been tried before. The cause is a check in
  the tool, not a decoding failure: its `lod-meta.json` writer takes either one source that already holds levels
  (a streamed SOG, an LCC) or local PLY files, and refuses anything else by its extension.
- **No PLY copy any more** (later the same day). Writing a whole scene out as a PLY only to pass that check is a
  wasted pass over the data. The tool's own readers return the same kind of source for every format, so a
  seven-line patch (`patches/@playcanvas__splat-transform@3.11.1.patch`, applied by pnpm at install, in Docker and
  in the desktop bundle) lets a level be a `.spz`, `.sog`, `.splat`, `.ksplat` or compressed PLY read in place.
  The four formats and the compressed PLY were run again this way: the same 3 levels (3 000, 1 500 and 750
  splats), one step fewer. The decimated levels are still written as PLY files in the temporary folder: the tool
  refuses `--decimate` on anything but a PLY output, by design. An install without the patch (the package
  fetched from npm alone) is detected and keeps the PLY copy. The patch is not sent upstream yet.
- **The options of a large-scene build** (2026-11-18). The form now carries what a streamed SOG of tens of
  millions of splats needs, each one a flag of the tool: harmonics kept (`-H`), a rotation (`-r`), a crop box
  (`-B`) and floater removal (`-F`), Morton order (`-m`), the smallest region that is split (`--lod-chunk-min`),
  splats per file, per level (`--lod-file-count`), encoding threads and the GPU adapter. When any of the first
  five is set, the finest level is written once, transformed, and every level is decimated from it; otherwise the
  input is read in place. A build that worked well on a 15 M-splat outdoor scene and a 174 M-splat interior:
  10 levels at 50 %, adaptive, base colour only, 8 m leaves of at most 64 K splats, regions under 16 K kept
  whole, 512 K splats per file at the fine levels and fewer at the coarse ones
  (`512,512,512,512,128,64,32,16,8,4`), on a GPU nothing else is using. Two things that build taught: far
  floaters stretch a file's bounds and make its stored positions coarser (4 cm against 1.5 cm at 100 m), so crop
  first; and adaptive decimation keeps the large far gaussians, so the coarse levels of an uncropped outdoor scene
  are mostly sky. Tried here on the 3 000-splat sample only (4 levels, harmonics dropped, rotated, sorted): the
  flags reach the tool and the output holds 3 000, 1 500, 750 and 375 splats with no harmonics.
- **rusty-tiles refused to write over its own output**, so a second run into the same folder failed. It is now
  called with `--force` (the app has already checked that the folder may be overwritten).
- **A folder is no longer taken for a point cloud because it holds a `.txt`.**

**pg2b3dm (PostGIS → 3D Tiles), the first tool whose input is not a file.** The dataset is an address,
`postgresql://user@host:5432/database`, and the table is an option. Tried against a PostGIS 3.4 container with a
table of 16 extruded buildings (PolyhedralSurface Z, EPSG:32631): one tile, displayed on the globe where the
coordinates say. A password in the address goes to the tool through `PGPASSWORD`; the run's log, its command
line and its record were searched for it and do not hold it. Without a password and without `PGPASSWORD` the
tool fails (it would ask on a console the app does not give it); the message is the tool's own stack trace.

**A Rust toolchain, fetched when the machine has none.** Spark's `build-lod` is source only. Before, a machine
without Rust was sent to rustup.rs. Now the package installs a toolchain itself, for the build only:

- rustup's installer (14 MB, SHA-256 pinned here) installs a pinned Rust (1.100.0, 135 MB to download) into a
  folder of the tools directory; `PATH`, the registry and the user's own Rust are not touched;
- the `windows-gnullvm` host is used because it links with the `rust-lld` it ships: **no Visual Studio build tools,
  no MinGW, no administrator**. The usual Windows host (MSVC) cannot link without Visual Studio; the `windows-gnu`
  one failed here for want of an assembler behind its `dlltool`;
- that host lacks a few Windows import libraries (bcrypt, advapi32…): they are copied from the `rust-mingw`
  component of the `windows-gnu` target into a folder the linker is pointed at;
- after the build the toolchain is removed: 9 MB stay, the program.

Tried with the machine's Rust hidden from the package (`TILED_PRIVATE_RUST=1`) and an empty tools folder: source
and toolchain fetched, built, toolchain removed, 180 s in all, and the program then tiled the splat sample. The
build itself was also run with an environment holding only the Windows folders on `PATH`. When the machine has a
`cargo` that fails (a Rust install without the C++ build tools), the package falls back to the fetched toolchain.
winget was not used: it installs rustup system-wide, and the default toolchain it brings still needs Visual Studio.

## The idea

Today the desktop app takes sources that are **already tiled** (COPC, Potree, SOG, LCC, RAD, I3S, 3MX, OSGB, Nexus)
and streams or exports them. The third flow, next to *Stream live* and *Export to a folder*: drop a **raw** file
(LAS/LAZ/E57, a mesh, a splat PLY), pick a tiler, and the app

1. gets the tool if it is not there yet,
2. shows the tool's own options in a form,
3. runs it as a subprocess, with its log, progress and Cancel,
4. hands the output to the existing flows: a COPC, a Potree folder, a streamed SOG or a RAD goes to `/stream`; a 3D
   Tiles folder opens as is.

We write no tiler ourselves. The value is in choosing, installing and chaining the official ones.

## Is the dependency side a nightmare?

Not if each tool is delivered the way its authors already ship it, and if we start with Windows, where most of them
publish a ready `.exe`. Four kinds of tools, from easiest to hardest:

| Kind | How it gets on the machine | Tools |
|---|---|---|
| **Already in our bundle** | nothing to install: the app ships Node | `@playcanvas/splat-transform` (PLY → streamed SOG) |
| **One binary per platform** | download the release asset, check its hash, unzip into the app's tools folder | PotreeConverter 2.x, gocesiumtiler, Obj2Tiles, fanvanzh/3dtiles |
| **Needs a runtime** | a portable runtime next to the tool, never a system install | mago-3d-tiler (Java: a portable JRE), py3dtiles (Python: a private environment made with `uv`) |
| **Heavy native stacks** | find an existing install first (QGIS ships PDAL and untwine), else a conda-style environment (`pixi`/`micromamba`) | PDAL `writers.copc`, untwine |

Docker images (py3dtiles, mago-3d-tiler, GeoSolutions' digital-twin-toolbox) are the fallback for the server, not
for the desktop app.

Release assets, versions and licences are **to be checked tool by tool** before anything is redistributed; the
table says how, not that every asset exists.

## How the app manages tools

- A **manifest** per tool, in the repo (`packages/tilers/tools.js`): name, version, download URL per platform, SHA-256, licence, the command
  line, and the form fields (each the tool's own flag, with its default and help text).
- **Detect before downloading**: the tool on `PATH`, a QGIS install for PDAL and untwine, or a path the user points
  to. A downloaded tool lives in the app's data folder, per version, so an update never breaks a running job.
- **Run** through the same subprocess runner as "Run in: CLI subprocess": stdout to the log panel, a progress
  parser per tool where its output allows, Cancel kills the process tree.
- **Chain**: the output folder is then opened by the stream or export flow, like any library item, and the run goes
  into the library history with its command line.

## Windows first

One platform makes it much smaller: one asset per tool, one path layout, one subprocess model. The known problem is
**Defender**: unsigned downloaded `.exe` files can be blocked, as our own launcher already is (see the Electrobun
notes). Signing our app does not cover third-party binaries, so the form should say which tool was blocked and how
to allow it. macOS and Linux come after, with the same manifests.

## Phases

1. **Windows, three tools** (**done**, as four: PDAL and untwine are separate entries): splat-transform (no
   download), PotreeConverter (one binary), PDAL/untwine found in a QGIS install. Proves detect, download, run, chain.
2. **More single binaries** (**done**): gocesiumtiler (points and splats), point-tiler, PotreeConverter 1.7,
   Obj2Tiles, fanvanzh/3dtiles.
3. **Runtimes** (**done**): py3dtiles in a private `uv` environment, mago 3DTiler on a Java runtime fetched next
   to it.
4. **macOS and Linux**, then the server variant (the same manifests, Docker images where they exist).

## Open questions

- Licences of each tool, for downloading on the user's behalf (we redistribute nothing if the app downloads from
  the official release page; to confirm per licence). gocesiumtiler and Obj2Tiles are AGPL-3.0, untwine GPL-3.0:
  the app runs them as separate programs and ships none of them.
- Spark `build-lod` (splat PLY to RAD) has no released binary: it would need a Rust build, or the authors to
  publish one.
- A tiler for a PLY or OBJ mesh without textures, and for E57 to Potree.
- Checksums: pinned per version in the manifest, so a moved or replaced asset fails loudly.
- Disk and memory: tilers are out-of-core but write large temporary folders; the form should show where.
- Which defaults to expose per tool, and which to hide behind "Advanced".
