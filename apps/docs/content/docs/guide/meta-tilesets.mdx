`/aggregate` answers one question: *"can I give a client a single URL that serves **all** our
datasets?"* — 10 Angkor scans, San Pietro, Sacré-Cœur, a Geghard point cloud, in one tileset.

It works because 3D Tiles supports this natively: a tile's `content.uri` may itself be another
`tileset.json`. So the endpoint fetches each child's root, derives a bounding sphere and geometric
error from it, and emits a parent whose children external-reference the child URLs.

```
GET /aggregate/tileset.json?url=<u1>&url=<u2>&…        # repeated form
GET /aggregate/tileset.json?urls=<u1>,<u2>,…           # comma form (each URL-encoded)
GET /aggregate/tileset.json?set=opendata|angkor|world|flai|aerometrex|…  # a named set (below)
    [&nest=auto|mercator|geodetic|flat]  [&bv=sphere|region]  [&ttl=<seconds>]
    [&format=…] [&only=…] [&exclude=…] [&hide=<id>] [&latest=1] [&from=…] [&to=…]
GET /aggregate/index.json?<same query>                 # one row per dataset, for UIs
```

## How a mosaic is built, step by step

Every request runs the same pipeline. Nothing below opens a dataset's *content*: only each child's
`tileset.json` is read, and a client later streams the tiles directly from each source.

1. **Select.** `?set=` / `?url=` / `?urls=` give the candidate children. `&format=`, `&only=`,
   `&exclude=`, `&hide=`, `&from=`/`&to=` filter them, and `&latest=1` drops superseded captures.
   Each child is one URL with, when known, an id, a name, a project, a scene, a date, a format and a
   licence. Sources that are not 3D Tiles are wrapped first: Potree and COPC through this server's
   `/stream` (with `&crs=` when the file declares none), and non-CORS 3D Tiles hosts through the
   tileset-aware `/proxy`.
2. **Read each child's root.** Each child `tileset.json` is fetched, 16 at a time and cached for a
   day (60 s for failures). Its root `boundingVolume` gives one **bounding sphere in ECEF**:
   - `box` and `sphere` are multiplied by the root `transform`;
   - `region` is already ECEF by definition.

   Its size gives the child's geometric error ([below](#how-a-childs-geometric-error-is-chosen)). A
   child whose sphere centre is near the Earth's core has no georeference, so it is set aside as
   *unplaced*.
3. **Group.** The spheres are arranged into a hierarchy, in one of three ways:
   - **`flat`**: the root lists every child directly.
   - **`mercator` quadtree**: web-mercator / Bing-quadkey cells, 2ᴸ × 2ᴸ per level.
   - **`geodetic` quadtree**: lon/lat cells on a 2 × 1 root, the subdivision a 3D Tiles implicit
     `QUADTREE` on a `region` performs.

   In both quadtrees each dataset goes to the deepest cell at least 4× its radius (at most level
   16). Its cell's base-4 path, the same digits as a Bing quadkey, is a key into a trie. The trie is
   path-compressed, so only branching cells become group tiles, and every group records its cell in
   `extras.cell` (key, level, Morton index). `nest=auto` is flat below 8 children and `geodetic`
   otherwise.
4. **Bound the groups.** A group's volume is either:
   - the minimal **sphere** enclosing its children's spheres (default); or
   - with `&bv=region`, the union of its children's lon/lat/height **regions**
     ([below](#region-bounding-volumes-bvregion)).

   Its geometric error is 2× the largest child's, so errors strictly decrease on refine and a distant
   group is never opened. The root takes the tighter of the union sphere and an **Earth-centred**
   sphere, or a region with `bv=region`.
5. **Emit.** The output is an explicit 3D Tiles 1.1 tileset:
   - every dataset is a leaf with `refine: "ADD"` whose `content.uri` is the child tileset (an
     external reference);
   - each leaf carries **tile metadata** (class `dataset`: `id`, `name`, `project`, `scene`,
     `date`, `format`, `licence`), so any 1.1 client can tell which dataset a tile is;
   - `asset.extras` records the nesting (depth, groups, root fanout), `failed` and `unplaced`
     children, and build timings (`build`).

   The whole mosaic is cached, keyed by the selection. `index.json` flattens the same cached tree.

**Why an explicit tree and not implicit tiling, and why no octree.** Implicit tiling allows one
content per available cell, while a cell here often holds several datasets, and most cells are
empty. So the tree would need extra levels anyway, and its subtree bitstreams would be almost all
zeros. The cells are still the implicit quadtree's cells, which is what `extras.cell` records. There
is no height (octree) split, because every dataset sits on the Earth's surface. A 2 × 1 lon/lat/height
octree would put nearly everything into its lowest height cells and separate nothing. The vertical
extent lives in the volumes instead: sphere radius, or `minH`/`maxH` with `bv=region`.

**What it costs, measured.** Almost all of a cold build is fetching child roots; the tree itself
takes milliseconds.

| Mosaic | Children | Cold build (fetch roots) | Tree | Warm, other scheme | Cached mosaic |
|---|---|---|---|---|---|
| `set=iconem` (Potree through `/stream`, 3D Tiles, COPC) | 692 | 10.8 s | 16 ms | 257 ms end to end (0 fetched) | 187 ms end to end |
| `set=flai` (113 national COPC overviews through `/stream`) | 113 | 4.2 s | 2.4 ms | | |
| `set=aerometrex` (through `/proxy`) | 12 | 1.8 s | 4.4 ms | | |
| synthetic, loopback (`debug-aggregate-nesting.mjs`) | 500 | ~0.3 s | ~5 ms | | |

The cached-mosaic time is mostly serialising and transferring the JSON. Every build reports its
own numbers in `asset.extras.build` (`childRoots`, `childRootsFetched`, `fetchMs`, `treeMs`), and
`index.json` repeats them.

### Search, markers and the dataset picker in the demo app

Whenever an `/aggregate` tileset is loaded, the demo app shows a search box over the globe, fed by
`/aggregate/index.json` — the same query as the tileset, flattened to one row per placed dataset
(`id`, `name`, `project`, `scene`, `group`, `date`, `format`, `lon`, `lat`, `height`, `radius`), plus
the `unplaced` and `failed` lists. The two can never disagree about which datasets a URL means: they
share one selection function and one cached mosaic.

- **Search** matches dataset name, project, scene, format and date as you type — accent-insensitive,
  every word must match, and **typo-tolerant**: one edit for words of 4–6 letters, two from 7
  ("mes aynek 2011" → MesAynak_2011, "venezzia"), also inside glued names like `MesAynak`. Exact
  matches rank first. It also queries the world through [Photon](https://photon.komoot.io) —
  OpenStreetMap, no key — from three characters. Arrow keys and Enter work; picking a dataset frames
  its bounding sphere, picking a place frames its extent.
- **Markers** (both renderers): one fixed-size dot per dataset on the ellipsoid, coloured by format
  (amber Potree, blue COPC, violet 3D Tiles). **Hovering shows a card** with the dataset, scene,
  project, format, capture date and size; clicking flies to it. A marker disappears once its dataset
  spans **more than 10% of the viewport height**, i.e. once the data speaks for itself. Cesium encodes
  that as a per-point `DistanceDisplayCondition` at `radius / (0.1 · tan(fovy/2))`; 3DTRjs evaluates
  the same formula in the vertex shader of one `THREE.Points` layer. Neither costs per-frame
  JavaScript. Hover uses `drillPick`, so a small dataset's marker still answers when a larger,
  already-loaded dataset covers it (Canal Grande under the Venice airborne scan).
- **The picker** (`in view N ▾`) lists the datasets that are in the frustum and at least 3% of the
  viewport tall — the ones rendering or about to — **grouped by platform scene**, each with a
  checkbox and its capture date. A group's **latest** button hides that site's older dated captures
  (a diachronic series such as Mes Aynak 2010 → 2022); **all** shows every piece (Venice: the airborne
  scan plus San Marco, Rialto and the palazzi, all 2021-06, meant to be seen together). Above the
  list: **format chips** derived from the index with their counts, a global **latest only** switch
  and a **capture-date range**. Hidden datasets keep a small grey marker so they can be found and
  brought back.

Every picker action rewrites the mosaic URL — `&hide=`, `&latest=1`, `&from=`/`&to=`, `&format=` (see
[below](#showhide-latest-only-and-dates)) — and reloads it without moving the camera. The picker has
no state of its own: a filtered view is still one shareable 3D Tiles URL.

<Callout type="info">
**"Why is a Bing dataset visible over Rome?"** It is not the `/bing` endpoint leaking into the mosaic:
the Iconem platform itself hosts a 3D Tiles asset named *Bing-Vatican - Cesium-it-62-rome-2020-subarea-vatican-1-48734*
in its *San Pietro Basilica* scene, so it is one of the 17 Iconem 3D Tiles children. Hide it with the
picker, or add `&exclude=Bing-Vatican`.
</Callout>

### Why not a 3DTRjs plugin for the markers

3d-tiles-renderer 0.5 has `MVTAnnotationsPlugin`, `GeoJSONOverlay` / `MVTOverlay` and the
`ImageOverlayPlugin`. All of them **drape** features onto loaded tile surfaces: they need geometry
under the feature and they scale with the ground. A "there is data here" marker has to be visible
precisely where nothing has loaded yet, at a constant pixel size, and MVT would mean serving vector
tiles for ~700 points. A plain `THREE.Points` layer that follows the tileset group's transform is
both simpler and correct; GeoJSON overlays would be the right tool for dataset *footprints*, later.

Presets backed by a machine-local set (the Iconem manifest) are only offered when the server reports
that set in `/aggregate/demo.json`, instead of being shown everywhere and failing with `unknown set`.

### What the Angkor set demonstrates

This is the interesting one, because the sites are **not** uniformly spread: 19 sit inside the Angkor
park a few km apart, while four PhnomKulen sites are ~30 km north-east. Nothing tells the aggregator
that — it sees 23 bounding spheres. It finds the split anyway:

```
[group r=23km]
  [group r=14km]                 ← the Angkor park, 19 sites
    …
    [group r=1km]
      • ElephantTerrace
      • AngkorThom_SouthGate
      [group r<1km]
        • Bayon
        [group r<1km]
          • Baphuon_SleepingBuddha
          • Phimeanakas
  [group r=3km]                  ← PhnomKulen, 4 sites, ~30 km away
    • PhnomKulen_01-2_KrorBeiKrab
    …
```

The innermost Angkor group — Bayon, Baphuon, Phimeanakas — is archaeologically correct: those three
are the monuments *inside Angkor Thom's walls*. That grouping came from bounding spheres alone.

Measured on the real endpoints: 23/23 children, **root fanout 23 → 2**, depth 8 (geodetic) or 7
(mercator). The `world` set: 33/33, fanout 2, depth 12.

Comparing `set=angkor` against the hand-authored merged root in the
[hierarchy explorer](/docs/guide/hierarchy-explorer) shows the point directly — same 23 datasets,
**root fanout 23 → 8**, at the cost of a few levels of depth.

<Callout type="warn">
**Why the explorer needs `external refs: 256` for mosaics.** `/stats` and the hierarchy explorer
follow external tileset references, each one another HTTP round trip, and stop after **64** by
default so that walking an arbitrary tileset stays bounded. An aggregate consists *only* of external
references (one per dataset, then each dataset's own), so even the 23-site Angkor mosaic passes 64
almost at once and reports `truncatedBy: ["external"]`, a partial tree. Raise the cap to 256 or 1024
in the explorer, or pass `&maxExternal=` to `/stats`, to see a whole mosaic.
</Callout>

Children can be **any** 3D-Tiles-serving URL — including this server's own `/stream`, `/convert`,
`/bing` or `/3dtiles-self-contained`. That is the point: one mosaic can mix COPC + Potree + LCC + RAD
+ remote 3D Tiles, and a child with no georeference can be globe-placed first via
[`/stream`'s placement params](/docs/guide/cli-usage). Unreachable
children never kill the mosaic — they are skipped and listed in `asset.extras.failed`.

## Flat is fine for 12 datasets and wrong for 500

With a flat root, every dataset is a direct child. The moment the root refines, **all** of them are
candidates — so at 500 datasets a client standing in Paris still considers Sydney.

`nest` builds an intermediate hierarchy from nothing but each child's root bounding volume — centre
and radius, which is all we can know without opening the datasets:

```
[group r=10km]           ← Versailles joins here
  [group r=3km]          ← Sacré-Cœur joins here
    [group r=2km]
      • Eiffel
      • Louvre
```

Two mechanisms then do the work, and it is worth being precise about which does what:

- **Culling** handles *rendering* — a group whose bounding sphere misses the frustum is skipped.
- **Geometric error** is what prevents the *fetch*. A group's GE is 2× its children's, so from orbit
  a site-sized group subtends a fraction of a pixel and the renderer never traverses into it — which
  means its children's `tileset.json` files are never requested at all.

Each dataset is placed at the **deepest level whose cell still comfortably contains it** (4× slack),
so a 200 m scan lands in its own city cell while a country-wide dataset stays shallow and is never
split across cells. The trie is then path-compressed, so you get continent → country → city only
where datasets actually diverge, not 16 levels of single-child nodes.

`nest=auto` (the default) nests once there are **8 or more** children; below that a flat root is
simpler and just as cullable.

## Two schemes, because Morton order is *not* a projection

<Callout type="info">
**Morton (Z-order) is an addressing scheme** — interleave the bits of a cell's x/y — and it says
nothing about which space those cells live in. Two different trees both use it, and they are not
interchangeable.
</Callout>

| `nest=` | Grid | Matches |
|---|---|---|
| `mercator` (aliases `1`, `true`, `webmerc`, `quadtree`) | 2^L × 2^L over the **web-mercator** square, latitude clamped at ±85.05° | Bing/OSM/slippy-map tiles. A **Bing quadkey is exactly the base-4 Morton code** of the cell — so this lines a mosaic's grouping up with the raster basemap and with [`/bing`](/docs/guide/bing-maps-3d)'s own quadkeys. |
| `geodetic` (aliases `morton`, `implicit`, `cesium`) | 2×1 cells at level 0, **longitude/latitude halved** per level | What **3D Tiles implicit tiling actually does**, and therefore what Cesium walks — its `GeographicTilingScheme`. |

The geodetic case is the one people assume is mercator, and it isn't. The implicit-tiling spec
subdivides the **root bounding volume in its own coordinate space**: for a `region`, "`x`, `y`, and
`z` refer to `longitude`, `latitude`, and `height`", and each child extent is a plain arithmetic
bisection of that range. Tiles *within* a level are then ordered along the Morton Z-curve — that is
the only place Morton enters. No mercator anywhere.

So: **Cesium's Morton order is not a web-mercator quadtree.** It is a geodetic quadtree indexed with
Morton codes. Bing's quadkey is a mercator quadtree indexed with the same codes.

Neither grouping is "wrong" — the nesting is a pure BVH either way, and any 3D Tiles client renders
both identically. They simply cut different seams, so pick the one that matches what you are
comparing against. Every group and dataset carries an `extras.cell` breadcrumb —

```json
"extras": { "cell": { "scheme": "geodetic", "key": "132000203123222", "morton": 436368298 } }
```

— so "why did this dataset end up here" has an answer from the tileset alone, without re-running the
server.

## Does it hold up at middleware scale?

Yes, with one caveat that had to be fixed rather than assumed. Measured by
`scripts/debug-aggregate-nesting.mjs` (500 synthetic datasets in 25 clusters, served from loopback):

| | `mercator` | `geodetic` |
|---|---|---|
| Root fanout (from 500) | **4** | **2** |
| Tree depth | 10 | 10 |
| Group nodes | 359 | 357 |
| Tree build, children cached | **2.4 ms** | **2.6 ms** |
| Cold build incl. 500 child fetches | \~156 ms (loopback) | — |

The tree build is negligible; the cost is entirely the N child round-trips. Hence two things:

**Child fetches are pooled at 16.** This is measured, not defensive. Firing all 500 at once with a
plain `Promise.allSettled` **lost more than half of them** — a mosaic came back with 232 datasets and
268 bare `fetch failed` entries, still answering `200`, because failed children degrade into
`asset.extras.failed` by design. It looked fine and was missing half the world, and the survivors
varied run to run so the tree was not even reproducible. A 16-way pool fixes it outright: the
children are independent round-trips, so 16 in flight already saturates the link and going wider only
buys socket exhaustion.

**Mosaics are cached whole, with a day-scale TTL** (`&ttl=`, default `86400` s), keyed on the exact
child set plus nesting scheme; each child's fetched root is cached the same way. Assembling 500
children must not happen per request — and a 3D Tiles client re-requests the root more than once per
session. But a mosaic that can *never* notice a child moved is a stale-data bug waiting to happen,
which is why the TTL is a day rather than forever. Failures get a much shorter TTL (60 s) so one dead
host cannot pin a degraded mosaic for a day. `&ttl=0` bypasses the cache **in both directions** — use
it while a dataset is actively being re-tiled.

## Local sets: mosaicking every Iconem dataset

Demo sets are committed; **local sets** are not. The Iconem set was generated by the script below
against the production platform: **692 share links** (658 Potree, 17 3D Tiles, 17 COPC) across 139
projects, of which **660 are placeable** (see [Datasets that cannot be placed](#datasets-that-cannot-be-placed)). Any `.local/aggregate-sets/<name>.json` (gitignored;
override with `AGGREGATE_SETS_DIR`) becomes `?set=<name>`, re-read on every request so a regenerated
manifest needs no restart:

```json
{ "label": "…", "entries": [
  { "url": "https://api.iconem.com/s/<token>/cloud.js", "format": "potree",  "name": "Geghard" },
  { "url": "https://api.iconem.com/s/<token>/<id>.json", "format": "3dtiles", "name": "Bayon_d2022" },
  { "url": "https://api.iconem.com/s/<token>/<id>.copc.laz", "format": "copc", "name": "…" } ] }
```

`potree` and `copc` entries are wrapped through this server's `/stream` automatically. `only=` /
`exclude=` match the entry's **name, project and scene** as well as its URL — necessary because a
share URL is an opaque token, so `only=_d2024` could never match `/s/<token>/cloud.js` alone.
`/aggregate/demo.json` lists local sets by name and count only, never their URLs.

### Generating the manifest: `scripts/iconem-share-links.mjs`

Enumerates every project → scene → Potree / 3D Tiles (and optionally COPC) asset on the Iconem
platform, ensures each has **one** live share link named `single-meta-tileset`, and writes the
manifest above.

```powershell
$env:ICONEM_EMAIL = "…"; $env:ICONEM_PASSWORD = "…"          # env only — never arguments
node scripts/iconem-share-links.mjs                            # dry run: lists what it would create
node scripts/iconem-share-links.mjs --apply                    # create missing links, write manifest
# → http://localhost:3001/aggregate/tileset.json?set=iconem&nest=geodetic
```

It was built from the platform's own source (`iconem/Backend`, `iconem/Frontend`) and tested against
`scripts/mock-iconem-api.mjs`, a mock that enforces the same contract — cookie `jwt`, `X-XSRF-TOKEN`
on writes, 100-row pages, non-unique share names — so the flow is proven without minting a real link.

- **Dry run by default.** Every share is public to whoever holds the URL.
- **Idempotent.** The platform does not enforce unique share names and every POST mints a new token,
  so the script reuses an existing live (non-revoked, unexpired) link of the same name. Running it
  twice creates nothing the second time.
- **No API keys exist on this platform** — it authenticates with an account email + password.

<Callout type="warn">
**COPC is opt-in (`--include-copc`), and for a real reason.** A share on a `las`/COPC asset is scoped
to the **whole project blob container**, not the one file: the link for a single `.copc.laz` grants
read + list on *every* blob in that project. Potree and 3D Tiles shares are scoped to their own asset
container. COPC shares also require an `admin` account — the `las` share routes are absent from the
expert permission list, so an expert gets `403`.
</Callout>

## Selecting a subset: `&format=`, `&only=`, `&exclude=`

`&format=potree|copc|3dtiles` (repeatable, or comma-separated) keeps only children of that source
format ("only the 3D Tiles", "only the point clouds") without maintaining a manifest per variant.
Local-set entries carry their format; an ad-hoc `?url=` child is typed from this server's own
`/stream`, `/tiles` or `/convert` `format=` parameter, and treated as 3D Tiles otherwise.

Overlapping captures are the motivating case. A site re-scanned yearly gives N tilesets covering the
**same ground** — Mes Aynak has one scan per year — and you usually want to see one, not all of them
stacked.

```
…/aggregate/tileset.json?set=angkor&only=PhnomKulen        → 4 of 23
…/aggregate/tileset.json?set=angkor&exclude=PhnomKulen     → 19 of 23
…/aggregate/tileset.json?set=angkor&only=Bayon&only=TaProhm → 2 of 23
…/aggregate/tileset.json?set=mysite&only=_d2024            → just the 2024 scan
```

Both are repeatable, case-insensitive **substring** matches against the child URL (`only` is applied
first, then `exclude`). Substring rather than regex on purpose: these live in query strings that
people edit by hand. An empty result is a `400` rather than an empty tileset, so a typo'd filter
fails loudly.

Filtering happens **server-side**, which is the point: the emitted tileset genuinely contains only
the chosen datasets, so a filtered view is still a plain 3D Tiles endpoint you can paste into Cesium
for Unreal. The URL *is* the whole state.

<Callout type="info">
**Overlap is already handled.** Every tile `/aggregate` emits — root, groups and dataset entries —
uses `refine: "ADD"`, so sibling datasets are drawn *together* rather than one replacing another.
`REPLACE` still applies *inside* each child tileset, which is what you want: replace between LODs of
one dataset, add between datasets. Nothing extra is needed for overlapping scans; filtering is about
not *wanting* to see them at once, not about correctness.
</Callout>

## Show/hide, latest only and dates

These params compose with the ones above and are what the demo app's picker writes.

| Param | Keeps |
|---|---|
| `&hide=<id>[,<id>…]` | everything except these datasets. `id` is the 10-hex-digit hash `index.json` reports, taken from the dataset's **source** URL, so it does not change with the server's origin. |
| `&latest=1` | among datasets covering the **same ground** at different dates, only the newest. |
| `&from=YYYY[-MM[-DD]]` `&to=…` | datasets whose capture date overlaps the range. **Undated datasets are kept**, so a timeline never silently empties a half-undated mosaic. |

```
…/aggregate/tileset.json?set=iconem&latest=1               → 625 of 660 placed
…/aggregate/tileset.json?set=iconem&from=2020&to=2021      → 356 (dated in range + undated)
…/aggregate/tileset.json?set=iconem&hide=266212bc81        → without Venice "General Airborne"
```

**What "same ground" means for `latest=1`.** Names are no guide, so the rule is geometric: centres
closer than 0.3× the larger radius, and radii within a factor of two. That groups a yearly re-scan
(Mes Aynak 2010, 2011, 2012, 2015 → 2022; Mosul al-Nuri 2018 → 2020; the INRAP excavation phases),
while leaving a **detail capture nested inside a wider one** alone. Piazza San Marco inside the Venice
airborne scan is much smaller, so both stay, and the airborne scan has a hole cut for it anyway.
A capture is superseded only if it **ended before** the newest one **started**. Mixed precision is
therefore handled honestly: `2022-05` and `2022-05-19` overlap, so neither replaces the other. It is
a heuristic: different sensors of one site (a 2022 LiDAR and a 2025 photogrammetry) count as the same
ground too. Use `&hide=` or the picker's per-site buttons when that is wrong.

**Where dates come from.** The platform's `date` field on each asset when set (128 of 692), otherwise
Iconem's naming conventions, most specific first, looking at the asset name, then the scene, then the
project (271 more):

| Pattern | Example | Date |
|---|---|---|
| `_dYYYYMM` / `_dYYYY` | `Vatican_…_d202412_p202501_epsg32633` | `2024-12` (`_p…` is the processing date, ignored) |
| `YYYY-MM` | `Palazzo Ducale - Venezia (2020-06)` | `2020-06` |
| bare year | `MesAynak_2012` | `2012` |

Years outside 1990–2035 are rejected ("Church of the Assumption, 1783" names a building, not a scan).
The share-link script writes `date`, `dateSource`, `projectId`, `sceneId` and `assetId` into the
manifest; re-running it in dry-run mode refreshes them without creating any link.

## Region bounding volumes: `&bv=region`

The nesting is already a quadtree: each group is a cell (`extras.cell` records its key, level and
Morton index). By default groups are bounded by **spheres**, the union of the children's balls.
`&bv=region` emits the same tree with group and root volumes as 3D Tiles `region`s
(`[west, south, east, north, minH, maxH]`), the union of each child ball's lon/lat/height box. That is
the volume an implicit quadtree would use, and it is much tighter for long thin groups.

A ball of radius `r` whose centre is `d` from the Earth's centre spans `asin(r/d)` of arc, plus 1%
for the gap between geocentric and geodetic latitude. Longitude widens by `1/cos` of the most poleward
latitude reached. A ball that touches a pole or crosses the antimeridian gets the full longitude
range, which is loose but never wrong. Dataset entries keep their own sphere, derived from their own
root. `scripts/debug-aggregate-nesting.mjs` checks that every dataset lies inside all of its
ancestor regions, under both schemes.

```
…/aggregate/tileset.json?set=iconem&nest=geodetic&bv=region
```

`region` is a core 3D Tiles 1.0 bounding volume, not something tied to implicit tiling. Cesium and
3DTRjs both cull and refine on it; the demo app's **Angkor — 23 sites (regions)** pill is the same
tree as the geodetic pill, so the two can be compared directly.

## Hand-built hierarchies still compose

Auto-nesting derives grouping from geometry alone. If you want a *semantic* hierarchy — by campaign,
by client, by year — nest the endpoint in itself: a child URL can be another `/aggregate` URL, since
3D Tiles external references compose to any depth. Auto-nesting and hand-nesting mix freely, so a
hand-authored "Cambodia" node can have an auto-nested mosaic of 40 Angkor scans underneath it.

## Inspecting the result

`/aggregate` output is a tileset like any other, so
[`/stats` and the hierarchy explorer](/docs/guide/hierarchy-explorer) walk it directly — including
following each child external reference — which is the quickest way to confirm a mosaic grouped the
way you expected.

## Sources that need care before you aggregate them

Three real sources were evaluated for the demo sets and each failed a different check. They are
documented rather than included, because each failure is a general lesson about aggregation.

**Aerometrex** (e.g. `demo3d.aerometrex.com/USA/US0014_Brooklyn_50mm_Oct_2021/Scene/Cesium_Brooklyn.json`)
— valid tilesets that fetch fine **server-side** but send **no `Access-Control-Allow-Origin`**, even
when asked with an `Origin` header (their preflight answers 403). A mosaic child pointing straight at
that host fails in any browser. **Solved by `/proxy`, which is tileset-aware:**
- for a JSON response with `asset` and `root`, it rewrites every `content.uri` (`Data/L13_0.b3dm`,
  nested `tileset.json`s) to an absolute `/proxy?url=…`, so the whole tree comes back through it;
- it also accepts S3's `application/octet-stream` for a `.json` path;
- a child with no query string inherits the parent's (Agisoft Cloud's access token).

Brooklyn's 1,003 tiles all stream this way. A manifest entry marks the host with `"proxy": true`.
Aerometrex's evaluation assets are also on Cesium ion: San Francisco is ion asset **1415196** and
Denver is **354307**; loading them needs an ion token.

<Callout type="warn">
**Vexcel needs a secret.** `api.vexcelgroup.com/v2/3d/tileset` answers with a root listing ~10
Australian collections, but its child URLs drop the `api_key`, and fetching one without the key
returns **403**. The key is a **credential** — it must never be committed to a demo set in a public
repo. Pass it per request with `?url=`, or wire it through an environment variable in your own
deployment.
</Callout>

**The Iconem STAC catalogue** (`app.iconem.com/api/stac/collections/tiles`) is a valid STAC
Collection whose `item_assets` declares a 3D Tiles entry point, and `…/api/stac/search?collections=tiles`
returns items — but **unauthenticated it exposes only a handful**, not the full catalogue. Enumerating
everything, and minting share links, needs credentials and is deliberately not automated here.

## Datasets that cannot be placed

A dataset in its own local frame (no georeference, no root transform) has its centre at the ECEF
origin, i.e. inside the Earth. It cannot be mosaicked: its "position" converts to an arbitrary
lon/lat and its sphere inflates the root past the planet's own radius. Such children are **excluded**
and listed in `asset.extras.unplaced` (on the Iconem set: 32 of 692). If *every* child is unplaceable
or unreachable, the endpoint answers **`422`** with both lists and a hint rather than a `500`: place
them first with `/stream/tileset.json?...&lon=<deg>&lat=<deg>` and they become ordinary children.

## The root bounding sphere

Worldwide mosaics are bounded by an **Earth-centred** sphere whenever that is tighter than the
greedy pairwise union of the children (whose radius overshot to 9 526 km for the Iconem set — larger
than the planet). Regional mosaics keep the tight union (Angkor: 23 km). The centre of a sphere that
encloses sites on several continents therefore sits inside the Earth — like the midpoint of a chord —
which is expected, not a placement bug. Viewers that decide "centre near the origin = local, unplaced
content" must also look at the radius: the demo app's 3DTRjs renderer treats a planet-sized sphere
as global data rather than re-anchoring it to the local frame.

## How a child's geometric error is chosen

The reference tile that points at a child tileset gates **when that tileset is loaded**, so its
geometric error means "the error of not showing this dataset at all", i.e. its size. It is
`max(child tileset GE, child root GE, bounding radius)`.

Taking the child's declared value alone broke on real data: Iconem's Angkor site tilesets declare
`geometricError` of √3 ≈ 1.73 at both tileset and root level for sites about 240 m across. Every group
above doubles from the value below, so the whole branch only refined within about 100 m of the
camera, and the mosaic loaded nothing from any sensible viewpoint. Well-formed tilesets (GE already
at least the radius) are unaffected.

## Limits worth knowing

- Grouping uses each child's **root bounding sphere**. A dataset whose root volume is far larger than
  its actual content (a loose root box) nests shallower than it deserves.
- `region` bounding volumes are already ECEF per spec, so the child root transform is deliberately
  not applied to them; box and sphere volumes are transformed into the parent frame.
- There is no reprojection or CRS negotiation — every child must already resolve to ECEF.
