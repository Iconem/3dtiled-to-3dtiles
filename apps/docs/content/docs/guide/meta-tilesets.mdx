`/aggregate` answers one question: *"can I give a client a single URL that serves **all** our
datasets?"* — 10 Angkor scans, San Pietro, Sacré-Cœur, a Geghard point cloud, in one tileset.

It works because 3D Tiles supports this natively: a tile's `content.uri` may itself be another
`tileset.json`. So the endpoint fetches each child's root, derives a bounding sphere and geometric
error from it, and emits a parent whose children external-reference the child URLs.

```
GET /aggregate/tileset.json?url=<u1>&url=<u2>&…        # repeated form
GET /aggregate/tileset.json?urls=<u1>,<u2>,…           # comma form (each URL-encoded)
GET /aggregate/tileset.json?set=opendata|angkor|world  # a curated demo set (below)
    [&nest=auto|mercator|geodetic|flat]  [&ttl=<seconds>]
```

## Try it — the demo sets

`?set=` expands server-side to a curated list of real, public, key-less tilesets, so the endpoint can
be *seen* rather than described. `GET /aggregate/demo.json` lists what each set contains.

| `set=` | What |
|---|---|
| `opendata` | The ten open datasets from 3D Tiles' own [RESOURCES.md](https://github.com/CesiumGS/3d-tiles/blob/main/RESOURCES.md#open-data) — Strasbourg, Clermont-Ferrand, Saint-Étienne, Lille, Planet's Angkor Wat SkySat, Utrecht, Soest, Aarhus, AGI HQ, Tokyo Minato-ku. Four continents, and all three bounding-volume kinds (`region`, `box`, `sphere`). |
| `angkor` | Iconem's Angkor campaign as **23 individual site tilesets** rather than its hand-authored merged root. |
| `world` | Both at once — 33 tilesets. |

```
http://localhost:3001/aggregate/tileset.json?set=world&nest=geodetic
```

`?set=` composes with `?url=`, so you can drop your own dataset into a demo mosaic without retyping
the other 33.

### What the Angkor set demonstrates

This is the interesting one, because the sites are **not** uniformly spread: 19 sit inside the Angkor
park a few km apart, while four PhnomKulen sites are ~30 km north-east. Nothing tells the aggregator
that — it sees 23 bounding spheres. It finds the split anyway:

```
[group r=23km]
  [group r=14km]                 ← the Angkor park, 19 sites
    …
    [group r=1km]
      • ElephantTerrace
      • AngkorThom_SouthGate
      [group r<1km]
        • Bayon
        [group r<1km]
          • Baphuon_SleepingBuddha
          • Phimeanakas
  [group r=3km]                  ← PhnomKulen, 4 sites, ~30 km away
    • PhnomKulen_01-2_KrorBeiKrab
    …
```

The innermost Angkor group — Bayon, Baphuon, Phimeanakas — is archaeologically correct: those three
are the monuments *inside Angkor Thom's walls*. That grouping came from bounding spheres alone.

Measured on the real endpoints: 23/23 children, **root fanout 23 → 2**, depth 8 (geodetic) or 7
(mercator). The `world` set: 33/33, fanout 2, depth 12.

Comparing `set=angkor` against the hand-authored merged root in the
[hierarchy explorer](/docs/guide/hierarchy-explorer) shows the point directly — same 23 datasets,
**root fanout 23 → 8**, at the cost of a few levels of depth.

<Callout type="warn">
`/stats` follows external tileset refs, and an aggregate is *made* of them — so walking one of these
demo mosaics hits the default 64-external-ref cap almost immediately and reports
`truncatedBy: ["external"]`. Pass `&maxExternal=256` to see more of it.
</Callout>

Children can be **any** 3D-Tiles-serving URL — including this server's own `/stream`, `/convert`,
`/bing` or `/3dtiles-self-contained`. That is the point: one mosaic can mix COPC + Potree + LCC + RAD
+ remote 3D Tiles, and a child with no georeference can be globe-placed first via
[`/stream`'s placement params](/docs/guide/cli-usage). Unreachable
children never kill the mosaic — they are skipped and listed in `asset.extras.failed`.

## Flat is fine for 12 datasets and wrong for 500

With a flat root, every dataset is a direct child. The moment the root refines, **all** of them are
candidates — so at 500 datasets a client standing in Paris still considers Sydney.

`nest` builds an intermediate hierarchy from nothing but each child's root bounding volume — centre
and radius, which is all we can know without opening the datasets:

```
[group r=10km]           ← Versailles joins here
  [group r=3km]          ← Sacré-Cœur joins here
    [group r=2km]
      • Eiffel
      • Louvre
```

Two mechanisms then do the work, and it is worth being precise about which does what:

- **Culling** handles *rendering* — a group whose bounding sphere misses the frustum is skipped.
- **Geometric error** is what prevents the *fetch*. A group's GE is 2× its children's, so from orbit
  a site-sized group subtends a fraction of a pixel and the renderer never traverses into it — which
  means its children's `tileset.json` files are never requested at all.

Each dataset is placed at the **deepest level whose cell still comfortably contains it** (4× slack),
so a 200 m scan lands in its own city cell while a country-wide dataset stays shallow and is never
split across cells. The trie is then path-compressed, so you get continent → country → city only
where datasets actually diverge, not 16 levels of single-child nodes.

`nest=auto` (the default) nests once there are **8 or more** children; below that a flat root is
simpler and just as cullable.

## Two schemes, because Morton order is *not* a projection

<Callout type="info">
**Morton (Z-order) is an addressing scheme** — interleave the bits of a cell's x/y — and it says
nothing about which space those cells live in. Two different trees both use it, and they are not
interchangeable.
</Callout>

| `nest=` | Grid | Matches |
|---|---|---|
| `mercator` (aliases `1`, `true`, `webmerc`, `quadtree`) | 2^L × 2^L over the **web-mercator** square, latitude clamped at ±85.05° | Bing/OSM/slippy-map tiles. A **Bing quadkey is exactly the base-4 Morton code** of the cell — so this lines a mosaic's grouping up with the raster basemap and with [`/bing`](/docs/guide/bing-maps-3d)'s own quadkeys. |
| `geodetic` (aliases `morton`, `implicit`, `cesium`) | 2×1 cells at level 0, **longitude/latitude halved** per level | What **3D Tiles implicit tiling actually does**, and therefore what Cesium walks — its `GeographicTilingScheme`. |

The geodetic case is the one people assume is mercator, and it isn't. The implicit-tiling spec
subdivides the **root bounding volume in its own coordinate space**: for a `region`, "`x`, `y`, and
`z` refer to `longitude`, `latitude`, and `height`", and each child extent is a plain arithmetic
bisection of that range. Tiles *within* a level are then ordered along the Morton Z-curve — that is
the only place Morton enters. No mercator anywhere.

So: **Cesium's Morton order is not a web-mercator quadtree.** It is a geodetic quadtree indexed with
Morton codes. Bing's quadkey is a mercator quadtree indexed with the same codes.

Neither grouping is "wrong" — the nesting is a pure BVH either way, and any 3D Tiles client renders
both identically. They simply cut different seams, so pick the one that matches what you are
comparing against. Every group and dataset carries an `extras.cell` breadcrumb —

```json
"extras": { "cell": { "scheme": "geodetic", "key": "132000203123222", "morton": 436368298 } }
```

— so "why did this dataset end up here" has an answer from the tileset alone, without re-running the
server.

## Does it hold up at middleware scale?

Yes, with one caveat that had to be fixed rather than assumed. Measured by
`scripts/debug-aggregate-nesting.mjs` (500 synthetic datasets in 25 clusters, served from loopback):

| | `mercator` | `geodetic` |
|---|---|---|
| Root fanout (from 500) | **4** | **2** |
| Tree depth | 10 | 10 |
| Group nodes | 359 | 357 |
| Tree build, children cached | **2.4 ms** | **2.6 ms** |
| Cold build incl. 500 child fetches | \~156 ms (loopback) | — |

The tree build is negligible; the cost is entirely the N child round-trips. Hence two things:

**Child fetches are pooled at 16.** This is measured, not defensive. Firing all 500 at once with a
plain `Promise.allSettled` **lost more than half of them** — a mosaic came back with 232 datasets and
268 bare `fetch failed` entries, still answering `200`, because failed children degrade into
`asset.extras.failed` by design. It looked fine and was missing half the world, and the survivors
varied run to run so the tree was not even reproducible. A 16-way pool fixes it outright: the
children are independent round-trips, so 16 in flight already saturates the link and going wider only
buys socket exhaustion.

**Mosaics are cached whole, with a day-scale TTL** (`&ttl=`, default `86400` s), keyed on the exact
child set plus nesting scheme; each child's fetched root is cached the same way. Assembling 500
children must not happen per request — and a 3D Tiles client re-requests the root more than once per
session. But a mosaic that can *never* notice a child moved is a stale-data bug waiting to happen,
which is why the TTL is a day rather than forever. Failures get a much shorter TTL (60 s) so one dead
host cannot pin a degraded mosaic for a day. `&ttl=0` bypasses the cache **in both directions** — use
it while a dataset is actively being re-tiled.

## Selecting a subset: `&only=` / `&exclude=`

Overlapping captures are the motivating case. A site re-scanned yearly gives N tilesets covering the
**same ground** — Mes Aynak has one scan per year — and you usually want to see one, not all of them
stacked.

```
…/aggregate/tileset.json?set=angkor&only=PhnomKulen        → 4 of 23
…/aggregate/tileset.json?set=angkor&exclude=PhnomKulen     → 19 of 23
…/aggregate/tileset.json?set=angkor&only=Bayon&only=TaProhm → 2 of 23
…/aggregate/tileset.json?set=mysite&only=_d2024            → just the 2024 scan
```

Both are repeatable, case-insensitive **substring** matches against the child URL (`only` is applied
first, then `exclude`). Substring rather than regex on purpose: these live in query strings that
people edit by hand. An empty result is a `400` rather than an empty tileset, so a typo'd filter
fails loudly.

Filtering happens **server-side**, which is the point: the emitted tileset genuinely contains only
the chosen datasets, so a filtered view is still a plain 3D Tiles endpoint you can paste into Cesium
for Unreal. The URL *is* the whole state.

<Callout type="info">
**Overlap is already handled.** Every tile `/aggregate` emits — root, groups and dataset entries —
uses `refine: "ADD"`, so sibling datasets are drawn *together* rather than one replacing another.
`REPLACE` still applies *inside* each child tileset, which is what you want: replace between LODs of
one dataset, add between datasets. Nothing extra is needed for overlapping scans; filtering is about
not *wanting* to see them at once, not about correctness.
</Callout>

## Hand-built hierarchies still compose

Auto-nesting derives grouping from geometry alone. If you want a *semantic* hierarchy — by campaign,
by client, by year — nest the endpoint in itself: a child URL can be another `/aggregate` URL, since
3D Tiles external references compose to any depth. Auto-nesting and hand-nesting mix freely, so a
hand-authored "Cambodia" node can have an auto-nested mosaic of 40 Angkor scans underneath it.

## Inspecting the result

`/aggregate` output is a tileset like any other, so
[`/stats` and the hierarchy explorer](/docs/guide/hierarchy-explorer) walk it directly — including
following each child external reference — which is the quickest way to confirm a mosaic grouped the
way you expected.

## Sources that need care before you aggregate them

Three real sources were evaluated for the demo sets and each failed a different check. They are
documented rather than included, because each failure is a general lesson about aggregation.

**Aerometrex** (e.g. `demo3d.aerometrex.com/USA/US0014_Brooklyn_50mm_Oct_2021/Scene/Cesium_Brooklyn.json`)
— a valid tileset, fetches fine **server-side**, but sends **no `Access-Control-Allow-Origin`** even
when asked with an `Origin` header. `/aggregate` can therefore derive its bounds, but the mosaic's
child `content.uri` points back at that host, so a *browser* client fails on it. This server's
[`/proxy`](/docs/api-reference) re-serves any URL with CORS — but proxying a **tileset root alone is
not enough**: its children are relative (`Data/L13_0.b3dm`) and a client would resolve them against
the proxy path rather than the origin host. A tileset-aware proxy that rewrites child URIs is the
missing piece; until then, treat non-CORS hosts as server-side-only.

<Callout type="warn">
**Vexcel needs a secret.** `api.vexcelgroup.com/v2/3d/tileset` answers with a root listing ~10
Australian collections, but its child URLs drop the `api_key`, and fetching one without the key
returns **403**. The key is a **credential** — it must never be committed to a demo set in a public
repo. Pass it per request with `?url=`, or wire it through an environment variable in your own
deployment.
</Callout>

**The Iconem STAC catalogue** (`app.iconem.com/api/stac/collections/tiles`) is a valid STAC
Collection whose `item_assets` declares a 3D Tiles entry point, and `…/api/stac/search?collections=tiles`
returns items — but **unauthenticated it exposes only a handful**, not the full catalogue. Enumerating
everything, and minting share links, needs credentials and is deliberately not automated here.

## Limits worth knowing

- Grouping uses each child's **root bounding sphere**. A dataset whose root volume is far larger than
  its actual content (a loose root box) nests shallower than it deserves.
- `region` bounding volumes are already ECEF per spec, so the child root transform is deliberately
  not applied to them; box and sphere volumes are transformed into the parent frame.
- There is no reprojection or CRS negotiation — every child must already resolve to ECEF.
