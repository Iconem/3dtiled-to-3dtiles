`/potree-lab` on the viewer app (`http://localhost:3000/potree-lab`) loads **one** Potree dataset at a
time with the point-rendering controls 3DTilesRendererJS added in
[#1742](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1742) (merged 2026-09-10). The upstream
example has no URL parameter — its datasets are hard-coded — so this page exists to point the same
renderer at *our* datasets.

Since 2026-10-28 the main 3DTRjs viewer uses the same `PointCloudEffectsPlugin` for every
point cloud (3D Tiles, `/stream` and native Potree leaves), with its *Point shape* and *Eye-dome
lighting* controls under *Tileset & LOD*; the lab remains the single-dataset bench with the debug
colour modes and the raw, middleware-free Potree path. On top of the plugin the viewer adds child-box
sizing for ADD-refined non-octree tilesets, see [Viewer](/docs/guide/viewer).

Open it from the demo app with **✺ potree lab** in the top bar. A raw `cloud.js` / `.copc.laz` in the
URL field opens as itself; a loaded point-cloud tileset (a `/stream` or `/aggregate` URL) opens in
`tileset` mode.

## What 3DTRjs's own loader reads (master, `70847eb`)

| Source | `PotreePlugin` (raw, in the browser) | Through our `/stream` (3D Tiles) |
|---|---|---|
| Potree 1.7 `cloud.js` (attribute **names**) | ✅ | ✅ |
| Potree 1.8 `cloud.js` (attribute **objects**) | ❌ upstream: `Cannot read properties of undefined (reading 'size')`. ✅ **with our patch** ([PR #1780](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1780/commits/c3381669)) | ✅ |
| Potree 1.x with LAS/LAZ node files | ❌ (always fetches `.bin`) | ✅ |
| Potree 2.0 `metadata.json`, DEFAULT encoding | ✅ | ✅ |
| Potree 2.0, BROTLI encoding | ❌ (`encoding` is never checked) | ✅ |
| COPC / LAS / LAZ / EPT | ❌ no loader in 3DTRjs (COPC is an open item of roadmap [#943](https://github.com/NASA-AMMOS/3DTilesRendererJS/issues/943)) | ✅ COPC |

**Potree 1.8 is most of our data.** 38 of 40 sampled Iconem clouds are 1.8. The version is decided
by file name only (`metadata.json` → v2, anything else → v1) and v1 attributes are looked up by name,
which is the same bug our own decoder had. `PotreeLoader.js` now has the patch,
`v1Attributes()`, that accepts 1.8's objects (their `size`, or `elements × elementSize`). With it an
Iconem 1.8 cloud loads raw (12,343 points on screen; 0 before). It is the first commit of PR #1780, described below.

**With upstream's plugins alone, COPC therefore goes through the middleware**, in `stream` mode (a
`.copc.laz` URL is detected), and the lab's `potree` mode is the raw, middleware-free path for Potree
only. The lab's own `copc` mode, below, reads a COPC in the browser.

## Controls

A **controls** select switches the camera scheme without reloading (`?controls=`):

| Choice | What it is |
|---|---|
| `EnvironmentControls (3DTRjs)` (default) | 3DTRjs's local-scene controls: pivot on the picked point, a fallback ground plane under the data |
| `GlobeControls (3DTRjs)` | 3DTRjs's globe controls, bound to the loaded tileset's group. The lab recentres content at the origin, so this is for comparing feel, not for real geography |
| `OrbitControls (three)` | three.js's own orbit around a fixed target |

Switching schemes keeps the camera where it is: the new scheme adopts the current focus (the orbit
target or the 3DTRjs pivot when one is active, else the point of the dataset under the screen centre,
else a point on the view axis), so OrbitControls' first update does not swing the view. **Double-click**
pivots on the picked point and moves halfway to it, **middle-drag** dollies toward the point under the
cursor (drag down = in), with every scheme. Picks go through the viewer's rule (`lib/picking.ts`):
never a hidden object, a wireframe, a transparent material or a back face. **inertia (s)**
is the damping half-life — 3DTRjs's `dampingFactor` is literally that time constant (their default
0.15 s glides long after the pointer stops; the lab uses 0.05 s), and the same half-life is mapped onto
OrbitControls' per-frame factor.

## Loading speed

Three knobs in the *tiles* folder, all in the URL (`dl`, `parse`, `cache`):

| Knob | Default | What it does |
|---|---|---|
| parallel downloads | 25 per origin | `downloadQueue.maxJobsPerOrigin` |
| parses / frame | 5 | `parseQueue.maxJobs` — each tile's points are decoded on the main thread, so this is the frame-time budget; what feels sluggish during camera motion is usually parsing, not bandwidth |
| tile cache (MB) | 400 | `lruCache.maxBytesSize`: parsed tiles kept for when the camera comes back |

The HUD shows the live queues (`N↓ M⚙`) and the cache size. The visible point count there is what
is actually drawn: with `error target` 2 on a city-scale Potree it is typically 1–3 M points, and the
budget, not the target, is what the lab lacks compared with Potree's own viewer (which stops at a point
budget rather than a screen-space error).

## The load modes

| `mode=` | How the dataset is read | Point sizing |
|---|---|---|
| `potree` | `PotreePlugin` reads `cloud.js` directly in the browser | **Adaptive, per point**: each point is sized by the deepest *active* octree node containing it, resolved in the vertex shader from a texture of the active node hierarchy |
| `stream` | This repo's `/stream` turns the same `cloud.js`, or a `.copc.laz`, into 3D Tiles (POINTS GLB), rendered through `PointCloudEffectsPlugin` | `sizing=` **adaptive**, per point like `potree`, for implicit `ADD` octrees ([3DTilesRendererJS#1792](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1792), vendored until released); **tile**, each tile's points from its own geometric error; or **fixed**, one world size |
| `copc` | **`CopcPlugin`** (`potree-lab/copcPlugin.js`) reads a `.copc.laz` directly in the browser by range requests, decodes it in workers and, with `place=globe`, places it from its CRS: no server | as `potree`: it is upstream's `PotreePlugin` with a COPC loader |
| `tileset` | **Any** 3D Tiles URL as is: typically an `/aggregate` mosaic of point clouds, kept regional with `&only=` | same as `stream` |

A COPC that declares no CRS takes one in the URL fragment: `…/overview.copc.laz#crs=EPSG:3812`, which
becomes `/stream`'s `&crs=`. The dataset list includes a flai COPC (Namur) and an aggregate, and for
example this shows Mes Aynak's newest capture with eye-dome lighting:

```
/potree-lab?mode=tileset&edl=0.6&url=http://localhost:3001/aggregate/tileset.json?set=iconem%26only=MesAynak_20%26latest=1
```

Both modes share the effects: point shape (`square`/`round`/`sphere`), minimum pixel size, eye-dome
lighting (strength, radius) and debug colouring by node / depth / tile.

The `potree` and `copc` modes also have **colour by** (`color=` in the URL): the file's colours,
elevation, intensity, classification (the ASPRS classes), return number, number of returns, point
source, user data, GPS time. The continuous ones are spread between the 2nd and the 98th percentile of
what is loaded, and the bar at the bottom gives that range. A COPC offers all of them. A Potree cloud
offers elevation and intensity only, because upstream's `PotreeLoader` decodes nothing else; the bar
says so when the attribute is missing and the file's colours stay.

Everything is in the query string, so any view is a shareable link:

```
/potree-lab?url=<cloud.js>&mode=potree|stream&shape=round&edl=0.4&scale=1&geSize=1&transform=meshopt
```

**`copc` mode.** A COPC octree has the shape of a Potree one (a cube halved per level, additive refinement, a
spacing halved per level), so the plugin keeps `PotreePlugin` whole and replaces its loader: copc.js for the
header, the info VLR and the hierarchy pages (read lazily, when the first node under a page is asked for),
laz-perf (WebAssembly) for each node's chunk. The bar at the bottom counts requests, megabytes, pages, the
decode time per million points and the time the page itself was held.

- **Decoding runs in workers.** The page fetches each chunk (so the request goes through the renderer's plugins
  like any tile) and hands it to one of min(4, cores - 1) workers, which returns position, colour and the
  attributes below as one transferred buffer; the geometry's attributes are views on it. When no worker can be
  started the same code runs on the page, and the bar says so; `workers=0` asks for that. Measured in headless
  Chrome on 2026-11-21 (software rendering and a busy machine, so read the ratios, not the times): on the first
  91 nodes of Autzen (3.0 M points, the renderer stopped), the page was held 640 to 910 ms per million points
  when it decoded itself, and 1.2 to 2.0 ms with the workers, about 500 times less; a 4 ms timer saw 420 to
  760 ms of gaps per million points before and none after. The decode itself costs the same wherever it runs
  (630 to 990 ms per million points in both cases), and the total time did not change: the network was the
  limit.
- **Attributes.** Beside position and colour (the file's RGB, or its intensity as a grey), each tile carries
  intensity, classification, return number, number of returns, point source, user data and GPS time (seconds
  after the file's first, as float32), for point formats 6, 7 and 8. That is 30 bytes per point where position
  and colour alone took 18; the plugin's `attributes` option keeps fewer.
- **Placement from the CRS.** With `place=globe` the root tile gets a transform to earth-centred coordinates,
  computed with proj4 from the WKT the file declares, by the method of the server's `georefFromCrs`: the centre
  of the octree goes to longitude and latitude, and the frame there is measured through the projection, which
  accounts for the unit (Autzen is in feet), the grid convergence and the scale factor at once. The vertical
  unit is read from the vertical part of a compound CRS. The lab has no globe: it turns that place back to its
  own frame (Y up, metres) and writes the longitude, latitude, height, unit and convergence in the bar. On
  Autzen (EPSG:2992, feet, with heights in US survey feet) the mean point of the root tile lands at 123.06870°W
  44.05610°N, 135 m, which is Autzen Stadium in Eugene; the matrix is 5 mm from proj4 applied to that point, and
  8 cm at a corner of the cloud 1 km from the centre. A file with no CRS, or one proj4 cannot read, stays in its
  own coordinates and the bar gives the reason. A CRS for a file that declares none goes in the URL fragment as
  a proj string or WKT (`#crs=+proj=lcc …`): proj4 in the browser knows no EPSG code but 4326 and 3857, where
  `/stream` has a table of them.

Checked the same day: Autzen from its S3 bucket, 45 tiles and 1.52 M points for the first view out of 48 range
requests and 14.5 MB, and placed, 44 tiles and 1.33 M points out of 47 requests and 13.0 MB; the production
build too (the worker and the wasm are emitted as assets).

What it lacks: a globe to see the placed cloud on; a geoid (a gravity-related height is taken as a height above
the ellipsoid); the bending of a cloud wider than about 20 km onto the ellipsoid, which the server does and this
does not (the frame is a plane, and the bar warns); a VPC; a legend for the colours. Colouring by an attribute
is done on the page, tile by tile, and is not counted in the time above. A request already sent to a worker is
not cancelled when its tile is no longer wanted. Nothing here was run on a real GPU. S3 answered one range
request in 15 to 25 s twice during these runs, and one failed request in five runs was seen earlier under 25
parallel requests (the plugin tries once more). The plan this is the first step of:
[tiled formats plugins](/docs/guide/planning/tiled-formats-plugin).

The dataset picker also lists the **manifests uploaded in the viewer** (Aggregate row, *your own manifest*): the
viewer keeps each file in this browser's storage, and the lab reads it from there, listing its Potree and COPC
entries one by one and the manifest as a mosaic of its point clouds (`tileset` mode).

The dataset picker lists public samples plus — **dev server only** — every Potree entry of the Iconem
share-link manifest (`.local/aggregate-sets/iconem.json`). Vite serves that file to **loopback clients
only** and returns `403` to anyone else, because it is a list of bearer-credential URLs and the dev
server binds every network interface.

The list is filled in after that fetch. lil-gui's `controller.options(list)` does not update a
dropdown in place — it destroys the controller and returns a new one, appended at the end of the
panel and without the old `onChange` — so the lab swaps in the returned controller, re-attaches the
handler and moves it back to the top. (Before that fix, picking an Iconem entry did nothing.) For
headless checks, `window.LAB` exposes `url`, `mode`, `tiles`, `rootLoaded`, `visibleTiles`,
`visiblePoints` and `errors`; in `potree` mode the URL lives in the plugin, so `LAB.tiles.rootURL` is
`null` and `LAB.url` is the one to read.

## Running the viewer on 3DTilesRendererJS master

To try unreleased renderer work in the **whole** viewer, not just this page, build the renderer from
source. The lockfile stays on 0.5.2:

```sh
node scripts/build-3dtr-master.mjs            # clone/update .local/3DTilesRendererJS, npm ci, build
cd apps/viewer && npm run dev:3dtr-master      # the viewer, aliased onto that build
```

`vite.3dtr-master.config.mts` aliases every `3d-tiles-renderer` entry point to the build and dedupes
`three` / `react` / `@react-three/fiber`, because the clone has its own copies and two `three`
instances break everything. On Windows, upstream's library build externalises its own `C:\…`
aliases and emits a 253-byte `index.js`; the script builds through a wrapper config that fixes the
`external` test without touching upstream files.

Why it breaks: its library config makes every module external unless the import starts with `.`, `/`
or `\`. Its own `packageAliases` are `path.resolve()`d, which on Windows gives `C:\…`, a string
that starts with none of those. So every internal module was treated as an external package and
`build/index.js` came out as 253 bytes of re-exports with mangled paths such as
`"C:Usersjonathan…"`. The wrapper (`.local/3dtr-vite.lib-config.win.mjs`, written by the script) only
replaces `external` with a test that also accepts absolute paths and `3d-tiles-renderer/…`
self-imports. Verified at `70847eb`: implicit `/stream` Potree
loads in the main viewer, and this lab renders a 149,695-point Mes Aynak aggregate with EDL. Once a
release ships the work, bump the dependency and delete `.local/3DTilesRendererJS`.

## What the viewer still adds to the plugins

The viewer used to carry vendored copies of `PotreePlugin` and `PointCloudEffectsPlugin`. They are gone
since `3d-tiles-renderer` `0.5.4`, which ships [PR #1780](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1780)
(Potree 1.8 attribute objects, a clear error for LAS/LAZ nodes and BROTLI encoding, a thrown error on
failed node downloads, `maxPointSize`, `sizeAttenuation = false`). Three local changes remain, as small
extensions rather than copies:

- `lib/potreePlugin.ts`: a hierarchy chunk whose download was aborted can be fetched again, and a node
  with no hierarchy entry stays a leaf. Both matter because `lib/staleLoads.ts` aborts in-flight requests.
- `lib/potreePlugin.ts`: colours stored as normalized uint16 (6 B/point) rather than float32 (12 B).
- `lib/addRefinePointSize.ts`: child-box sizing, see [Viewer](/docs/guide/viewer).

A public Potree 1.8 reproducer for the attribute bug: Iconem's STAC catalogue at
`https://app.iconem.com/api/stac/collections/pointcloud` lists 1.8 clouds among its items (32 of the
first 80), e.g. item `1cc42849-d27d-4954-9d52-fac110d8a480` (3.2 M points). Its `data` asset is a
signed blob URL valid for a day whose query string must be forwarded to every node request, so a
`fetchData` override is needed when loading it outside the Iconem share-link proxy.

## What comparing the two modes showed

<Callout type="warn">
**Our point clouds were rendering washed out everywhere — fixed.** glTF defines `COLOR_0` as
**linear**, but every point writer here (live COPC/Potree, offline COPC/Potree/LAS, `.pnts` upgrade)
copied display-encoded sRGB straight in. Side by side on Geghard, `potree` mode showed the site's
greens and browns while `stream` mode showed the same points pale and whitish. Colours are now
linearised on write (a 16-bit lookup table, so no `pow()` in the tile hot path); splat centroids,
which are already linear, opt out. Conversions cached to disk before the fix are ignored — the
`/convert` cache key now carries an output version.
</Callout>

**Per-tile sizing is not enough — per-point sizing is what makes Potree look right.** `/stream` point
tilesets refine **additively**, so every ancestor tile stays on screen with its coarser, sparser
points. Sizing points from their *own* tile's geometric error makes those ancestors draw large blobs
under the fine detail. Potree avoids exactly this by sizing each point from the *deepest active node
covering its position*.

That is also the answer to "can the density be passed down to plain 3D Tiles endpoints?": **yes, but
it has to be the per-point scheme**, not a per-tile size:

- For implicit-octree tilesets (our `/stream` COPC and Potree), a tile's `(level, x, y, z)` is exactly
  a Potree octree key, and its geometric error is the point spacing — so the same active-node texture
  can be built without any Potree metadata.
- [3DTilesRendererJS#1792](https://github.com/NASA-AMMOS/3DTilesRendererJS/pull/1792) adds it to
  `PointCloudEffectsPlugin` as `adaptivePointSize`. Until it is released, the lab uses a copy of the
  PR's three files (`src/potree-lab/vendor`), for `stream` and `tileset` with `sizing=adaptive`; the
  main viewer stays on the 0.5.4 build and its own per-tile child-box sizing (`addRefinePointSize.ts`).

## Limits

- **Potree 1.x (`cloud.js`) is the tested path.** The plugin also reads 2.0 (`metadata.json`); the
  Iconem platform only produces 1.x today.
- Splat rendering cannot be judged in headless verification: Spark splats render as a dark blob under
  software GL on **both** `0.4.28` and `0.5.2`, so the renderer upgrade is neutral there but splat
  quality is unverified until checked on a real GPU.
- `stream` mode recentres georeferenced tilesets with `ReorientationPlugin`, and frames on a bounding
  **sphere** — a box around a rotated ECEF box is inflated and framed sites several times too far away.
