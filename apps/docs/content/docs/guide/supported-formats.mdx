## Introduction: The intent (online, range-streamed)

This started as a set of Node.js SDK/CLI, standalone-packaged, **converters**: take a *tiled / LoD source format* — HLOD Hierarchical Level of Detail, tiled point clouds, meshes, or 3D Gaussian splats (COPC, Potree, I3S, stream-SOG, LCC, RAD, 3MX, GeoSplats, …) — and
turn it into OGC **3D Tiles 1.1** (standard mesh primitives, `TRIANGLES`, `POINTS`, splats via `KHR_gaussian_splatting` +
`KHR_gaussian_splatting_compression_spz_2` GLB tiles). The unifying idea behind every converter is
the same: translate each of the tree-hierarchy and tile-geometry as-is, since each source format is already *some spatial tree of pre-tiled, LoD'd content* — so the
converter just maps that tree onto a 3D Tiles HLOD tree, implicit (octree/quadtree) or explicit (arbitrary), and re-encodes node content into one shared
output. The decode differs per format; the output is uniform.

It has since grown into an **on-the-fly streaming middleware** (`packages/tile-server`, the offline
converters' live counterpart): point it at a `<format>` source URL and it serves a 3D Tiles tileset
*live*, so any 3D-Tiles-compatible client — browser/JS viewers, CesiumJS or its native plugins
(Unreal, Unity, Nvidia Omniverse, Open-3d-Engine), GIS software (QGIS, ESRI etc), anything that speaks the OGC standard — can consume any of these tiled
formats **without a pre-conversion step**, with tile-hierarchy/content **caching** and **prefetching**
tunable per use case (`cache=none|hierarchy|all`). A viewer (vite-served React app) based on CesiumJS and 3DTilesRendererJS is the
reference client, and doubles as a **bbox + geometric-error-aware crop/extract** tool (`/extract/*`) for
pulling a sub-region, with user-controlled Geometric Error target precision, of any of these formats back out as LAS/COPC/GLB/SPZ/SOG/PLY.

### Towards a TiTiler for 3D

A **TiTiler equivalent for 3D formats**: middleware that reads cloud-native, internally tiled 3D
formats and streams OGC 3D Tiles 1.1 **on demand** — transcribing the source octree/hierarchy into a
3D Tiles tree and converting raw node geometry to glTF/GLB, served over HTTP Range so nothing is
re-encoded or re-sorted. Like TiTiler for COG: zero re-tiling, zero copy.

> The intent: fully online, fetching only the required portions of the underlying format hierarchy
> to build the 3D Tiles JSON hierarchy, then — when GLB tiles are requested — fetching via range
> requests the corresponding `{copc, stream-sog, lcc, potree, etc}` contiguous memory block just to
> build the requested tile.

The end state is the same model generalised to every internally-tiled format
(streamed-SOG chunk runs, LCC unit LOD runs, Potree octree-node byte ranges, …): a per-format
"range adapter" mapping a requested 3D-Tiles key → the source byte range to fetch and transcode.

### Tiled point clouds → 3D Tiles

| Format  | Hierarchy / subdivision | Node (leaf) content | Refine | Intermediate nodes | Metadata location | HTTP range |
|--------|-------------------------|---------------------|:------:|--------------------|-------------------|:----------:|
| **[COPC](https://copc.io)** (Cloud Optimized Pointcloud) · [spec repo](https://github.com/copcio/copcio.github.io) | **octree** (EPT-style) | LAZ-compressed LAS points | ADD | octree nodes (accumulate) | COPC VLR + hierarchy pages | ✅ designed for range reads |
| **[Potree](https://github.com/potree/PotreeConverter)** (v1 and v2) · [2.0 format](https://github.com/potree/potree/blob/develop/docs/) | **octree** (named `r`/`r0`..`r7`) | points: position int32×3·scale+offset + rgb (2.0 `octree.bin` / 1.x per-node `.bin`) | ADD | octree nodes (accumulate) | 2.0 `metadata.json`+`hierarchy.bin` (22 B/node) · 1.x `cloud.js`+`.hrc` | ✅ (2.0 single octree.bin; 1.x per-node files) |

**A virtual point cloud (`.vpc`) is an index, not a tiling.** PDAL and QGIS write one to treat a folder of
LAS/LAZ/COPC tiles as a single dataset: a STAC ItemCollection with each file's extent, CRS and point count. It
streams as `/stream/tileset.json?format=vpc&url=<….vpc>`: one mosaic whose leaves are the COPC streams of its
items, placed from each item's own `proj:bbox` so that the root is built without opening any of them (1 000
tiles: a 643 KB root in 161 ms). Only its COPC items are streamed; plain LAS/LAZ items are skipped and
counted. See the [VPC page](/docs/references/pointclouds/vpc).

**Potree 1.x point counts are not reliable.** PotreeConverter's 1.7 code writes `numAccepted` to the `.hrc`, and only an
inner node adds to it: a leaf keeps its points in `store`. So a leaf can be recorded with **0 points while its `.bin`
holds thousands**. On one 1.3 billion point Iconem cloud that was 169,134 of 209,474 nodes, about 3/4 of the points. It is
common in format 1.8 and rarer in 1.7. The readers here follow Potree: a listed node exists, and its real count comes from
the size of its `.bin` when it is read. They do not fetch that size up front, as one request per node would cost 209,474
requests on that cloud, for a number nothing needs before the tile is read.

Potree 2.0 and COPC do not have this: on `lion`, `heidentor` and `eclepens` from potree.org, every node's count matches
its bytes and the counts add up to `metadata.json`, and COPC's hierarchy adds up to its LAS header.

**A hierarchy read that fails is an error, not an empty branch**, for every format: see [When a read fails](#when-a-read-fails).
On export, [`hierarchyErrors`](/docs/guide/desktop-app#export-to-a-folder) chooses between stopping and carrying on without it.

**LAS dimensions travel with the points, when asked.** `&attributes=Intensity,Classification` on the `/stream` tileset
URL names the dimensions by their PDAL names, in any case (`attributes=all` takes every one the source has); the tileset
passes the parameter on to its tile URLs. A COPC tile's GLB then carries them next to `POSITION` and `COLOR_0` as glTF
custom attributes, raw: `_INTENSITY` (uint16), `_CLASSIFICATION` (uint8), `_RETURN_NUMBER`, `_NUMBER_OF_RETURNS`,
`_POINT_SOURCE_ID`, `_USER_DATA`, `_SCAN_ANGLE` (float32), `_SCANNER_CHANNEL`, `_INFRARED`, the flags
`_SCAN_DIRECTION_FLAG`, `_EDGE_OF_FLIGHT_LINE`, `_SYNTHETIC`, `_KEY_POINT`, `_WITHHELD`, `_OVERLAP` as 0/1 bytes, and
`_GPS_TIME` as float32 seconds from the tile's earliest time, which the primitive's `extras.gpsTimeOffset` gives back
(glTF has no float64 accessor). A Potree tile has `Intensity` and `Classification`. Off by default: each adds 4 bytes a point (glTF aligns
vertex attributes to 4 bytes, so a 61 k-point Autzen tile grows from 1.22 MB to 1.71 MB with both), and the viewers here ignore them. The offline converters always write them. A client that reads
custom attributes (Blender's 3D Tiles add-on, QGIS, a Cesium style) ramps them itself. Intensity is not mapped into
`COLOR_0`: its range depends on the scanner, so a cloud without RGB stays white.

For both, a tile's `geometricError` is the **point spacing at its depth**: Potree's declared spacing
and COPC's info-VLR `spacing`, halved per level (fallback: the root cube / 128). A 2 px error target
then stops refining where points are two pixels apart, and the viewers' adaptive point size reads the
spacing straight from the error. (Until 2026-10-29 COPC tiles declared their cube *diagonal* / 2^level,
100–200× too much, which refined every node to two pixels wide — see the changelog.)

### LCC and LCC2

XGRIDS replaced LCC with LCC2 in 2026 ([LCC whitepaper](https://github.com/xgrids/LCCWhitepaper),
[LCC2 whitepaper](https://github.com/xgrids/LCC2Whitepaper), spec 0.0.3 of June 2026; both carry XGRIDS' own
licence, which asks for attribution and keeps derivatives of the format as open). We read both, LCC2 since
2026-11-09 with `.sog`, `.spz` and `.ply` chunks ([notes on the format and its public samples](/docs/references/3dgs-splats/lcc2)).
What changed, from the two whitepapers and `splat-transform`'s readers (`read-lcc.ts`, `read-lcc2.ts`):

| | LCC | LCC2 |
|---|---|---|
| Files | `meta.lcc` (JSON), `Index.bin`, `Data.bin`, optional `Shcoef.bin`, `Environment.bin`, `Collision.lci` | one `.lcc2` JSON, `data/3dgs/*` as `.sog`, `.spz` or `.ply`, optional `data/mesh/*.ply` and `.btree` BVH files |
| Spatial structure | a flat XY grid of units (`cellLengthX/Y` metres from the bounding box's corner), each unit a stack of LOD levels | an n-ary tree of nodes (`id` like `0-1-1-7`), each with its own box and children; `splat-transform` treats it as an octree |
| Index | `Index.bin`, one fixed record per unit: cell x and y, then per LOD a count, an offset and a size into `Data.bin` | the tree is inside the JSON: a node names a file by index and a row range in it (`start`, `count`); neighbouring nodes of one level share a file |
| LOD | `totalLevel` levels, bound to the storage layout: a unit's LOD is a byte range | `totalLevels`, independent of storage; node LOD = `totalLevels − depth`; an optional `virtualLoD` describes further downsizing |
| Splat encoding | its own fixed 32-byte record: `f32` xyz, `rgba8`, `u16` scales against scene-wide min and max, a 10-10-10-2 rotation, `u16` normals | delegated to the payload codec, one per dataset (`splatType`): SOG's WebP planes or SPZ; `splat-transform` reads those two, not the PLY variant |
| Spherical harmonics | `Portable` = degree 0; `Quality` = degree 3 in `Shcoef.bin`, 64 bytes a splat | inside the SOG or SPZ chunks, must be the same degree in every chunk |
| Environment and collision | `Environment.bin` (its own min and max) and `Collision.lci` (meshes and a serialized BVH) | an `env` entry naming a splat file; per-node `mesh` and `bvh` entries, `.btree` files of 32-byte nodes |
| Georeferencing | `epsg`, `offset`, `shift`, `scale` | same names; `offset`, `shift` and `scale` marked reserved |
| New in LCC2 | | `splatExtraAttributes` (instance, semantic, thermal), `renderingHints` |

For the converter and the server this means: an LCC tile is a byte range of `Data.bin` decoded by a loop, so it
streams over range requests with no decoder dependency. An LCC2 tile is a row range of a SOG chunk: a node's rows
cannot be fetched alone from a SOG, whose WebP planes decode whole. So `format=lcc2` is an adapter of its own that
shares LCC's frame and georeferencing and runs on streamed SOG's machinery: the chunk is decoded by `readSog`, kept
in the same cache, and tiles are cut from it by the same code. The tree comes from the manifest alone, node for
tile. The offline converter (`3dtiled scene.lcc2 out`, inside `lcc-to-3dtiles`) writes the same tiles through
streamed SOG's chunk task. What a chunk's ZIP makes possible is leaving its `shN_*` planes on the server, 27 % of
the Tunis sample's bytes.

| Format | What exists | Why it is not what runs here |
|---|---|---|
| Potree 1.x and 2.0 | Potree's own loaders, written for three.js in a browser | They load into a renderer's scene, node by node on its camera. A converter needs one node's bytes turned into arrays, with no scene; the readers are a few hundred lines. |
| LCC (XGRIDS) | XGRIDS' LCC Web SDK; `@playcanvas/splat-transform` reads `.lcc` and LCC2 | The SDK is a renderer: it unpacks splats in a shader and exposes no decode call (our byte layout is taken from that shader). `splat-transform` 3.x reads LCC as a lazy source that can be asked for one chunk, but its chunks are its own (a LOD level cut every 65 536 splats), not the units of `Index.bin`; a tile here is one unit at one LOD, a byte range named by `Index.bin`, which is what lets it be streamed over range requests. The loaders.gl decoder is the one to adopt, or to compare against, once 5.0 is stable. |
| 3MX | none in JavaScript that we found; Bentley's SDK is native and closed | The `.3mxb` container is a JSON header and a list of buffers; its meshes are OpenCTM, decoded by the vendored `js-openctm`. |
| OSGB | OpenSceneGraph itself (C++, what `fanvanzh/3dtiles` and every desktop converter link); `osg-serializer-js` / `osgb` on npm (unmaintained, file versions up to about 100, no block sizes past them); `flywave/go-osg` (Go) | No native module can be built or shipped here, and the JavaScript reader stops before the versions DJI Terra writes (131). The format is a fixed layout per class and version: the reader is a table of fields, 500 lines, written from the layout and checked on 3 918 real files. |
| Nexus | Nexus itself (C++, GPL) and its JavaScript loader `nexus.js` (MIT, for three.js); Corto's C++ and its JavaScript decoder (MIT) | The file is a fixed layout of four tables and per-node streams, 270 lines to read; only the decoders are taken, unchanged, so that nothing GPL is linked. |

### The glTF-Transform patch, explained

I3S and Bing globe tiles are written with [glTF-Transform](https://gltf-transform.dev) since 2026-11-05, and a
patch of it ships in `patches/` (applied by pnpm at install, in Docker and in the desktop bundle). What it is for:

A GLB holds its vertex data in one binary blob. For a mesh tile that blob is a few arrays laid end to end:
all the positions, then all the normals, then all the texture coordinates, each a plain run of 32-bit floats. We
already have each of those arrays in memory as a typed array (`Float32Array`), and a typed array *is* already the
exact bytes the file needs, in the right order. Producing the blob should be a copy, the way `memcpy` is a copy.

glTF-Transform's writer was built for the other layout too, *interleaved*: position, normal and UV of vertex 0,
then those of vertex 1, and so on. Its one routine handles both layouts the same way: for every vertex, for
every attribute, for every component (x, then y, then z), it reads one number from the typed array and writes it
into the output through a `DataView`, which is JavaScript's byte-by-byte writer. For a tile of 300 000 vertices
with three attributes that is a few million small calls, and it took 88 ms of a tile's time. The arrays were
already in the right shape; the routine just did not notice.

The patch adds one check at the top of that routine: if this buffer view is made of a single attribute, and its
elements are not padded (a `VEC3` of floats is 12 bytes, which needs no padding; a `VEC3` of bytes would), then
the typed array's bytes are the output, and they are copied in one call. Otherwise the old loop runs. For the
same tile the write drops to 13 ms, and the file is identical to the byte: the output hash of the I3S run did not
change. Ten lines, in `interleaveAccessors` of `packages/core/src/io/writer.ts`. The pull request to send it
upstream is drafted (see the [future work](/docs/guide/todo-future-work) page); merged, our patch goes away. Until
then it is pinned to glTF-Transform 4.4.0: pnpm refuses to install if the dependency moves without it.

### What tile workers gain, measured

The same tiles, byte for byte, with and without workers. Offline converters, local disk, in seconds. The machine is
a laptop (Intel i7-12800H: 6 performance cores, 8 efficiency cores, 20 threads) that was rendering in Blender
during most of these runs, so take the ratios, not the figures:

| Converter | Dataset | One thread | 4 workers | 8 workers |
|---|---|---|---|---|
| COPC | Autzen, 278 tiles | 15.7 | | 5.3 |
| I3S | New York buildings, 5 882 tiles, 7.8 GB | 95 | | 33 |
| RAD | Coit tower, 778 tiles | 33 | 23 | 17 |
| LCC | Guan temple, 154 tiles | 9.6 | 5.2 | 4.6 |
| Streamed SOG | skatepark, 20 chunks, 2 054 tiles | 23 | 12 | 13 |
| Streamed SOG | Roman parish, 131 chunks, 37 725 tiles | 90 | | 55 |

The gain follows how much of a run is the per-tile work. COPC and I3S are almost only that. A RAD run first reads
the whole file and builds its tree on one thread. Every worker of a SOG run first loads `splat-transform`, nearly two
seconds each, which a small scene never earns back. On the live server the splat formats gain least: the gzip of an
SPZ payload already ran off the main thread (Node hands it to its own thread pool), and the remote samples measured
were slower to fetch than to decode.

COPC and Potree were moved onto the shared tile loop after this table was taken; measured again against their
former loops, interleaved, three runs each: same bytes, and the same times within the noise of the machine (Autzen
17.3 against 17.5 s on one thread, 4.6 against 4.7 s with 8 workers; Texas, 1 002 tiles, 42.7 against 40.5 s and
9.8 against 11.0 s; Potree `lion_p2`, 1 741 tiles, 4.0 against 3.9 s and 2.3 against 2.4 s).

**Why the big SOG scene gains less than 2×.** Taken apart on the Roman parish scene (same laptop, Blender running,
so the absolute figures are worse than the table's):

| Run | One thread | 8 workers |
|---|---|---|
| Whole conversion | 130 s | 59 s |
| The same with the tile files not written | 78 s | 36 s |
| Sum of the time the threads spent decoding chunks | 30 s | 59 s |
| Sum of the time the threads spent cutting, packing and gzipping tiles | 39 s | 124 s |
| Before the first chunk starts (start-up) | 1.9 s | 6.7 s |

- **Writing 37 725 small files costs 50 s on one thread and 22 s with workers**, about 40% of the run either way:
  creating a file on Windows (NTFS plus Defender's scan of each new file) is a millisecond or more, serialised in
  the kernel, not in our code. Fewer, larger tiles would be the only cure, and the SOG tree decides the tiles.
- **The same work takes 2.6 times longer per thread when eight threads do it** (70 s of thread time becomes
  183 s). That is the hardware: eight workers plus the main thread and Node's pool land on six fast cores and
  eight slow ones that share one power budget, with Blender on them too. Four workers take the same wall time as
  eight (37 against 36 s without writes), sixteen are slower (42 s). On a desktop with more full cores the ratio
  would be better; the code is not the limit here.
- **Start-up is 6.7 s with workers against 1.9 s without**: eight workers each load `splat-transform` (1.8 s alone,
  near 5 s when eight load at once). Node's compile cache (`NODE_COMPILE_CACHE`) does not help: the cost is running
  the module's top level (it brings the PlayCanvas engine in), not parsing it.
- Not the cause: the libuv pool (raising `UV_THREADPOOL_SIZE` to 16 gained 5 s), chunk order (the largest chunk is
  1.2 s of work; chunks now go out largest first anyway), or `splat-transform` 2.6 against 3.10 (same times).
- Kept from this: chunks are handed out largest first, and a tile worker gzips in place rather than through the
  pool the whole process shares. Both leave the bytes as they were.

**A streamed-SOG chunk is decoded once, not once per tile.** A chunk is a set of WebP images holding half a million
splats or so, and dozens to hundreds of tiles are ranges of it. Offline, tiles are grouped by chunk and each chunk
is decoded once (once on whichever worker takes it, with workers). On the live server the decoded chunk is cached,
while it is still decoding too, so tiles of one chunk asked for together share one decode. That cache holds 24
chunks per scene (`TILED_SOG_CHUNK_CACHE`): a decoded chunk is 30 to 45 MB, so 24 is already up to a gigabyte, and a
chunk evicted and needed again costs a third of a second to decode. A crawl export that walks more than 24 chunks
at once therefore decodes some of them twice; raising the setting trades memory for that.

## 3D Tiles → 3D Tiles transcodes

The input is *already* 3D Tiles — these are tileset-level transforms (the live/streaming-flavored
counterparts to [`3d-tiles-tools`](https://github.com/CesiumGS/3d-tiles-tools)).
Served live by the **`/3dtiles-tools`** endpoint (`packages/tile-server/3dtiles-tools-live.js`):
tileset JSON is rewritten once and cached; each tile is converted on demand (like `/stream`).

**`tool=implicit-to-explicit`** — read a tileset with `implicitTiling` (OCTREE/QUADTREE) + `.subtree`
files, walk the availability bitstreams, and emit an **explicit** nested tree (derived boxes via the
same `octreeSubCube`/`cubeToBox` core helpers as the octree converters). Per-tile `.b3dm`/`.pnts`
content is converted to glb on the fly; `.glb` is proxied as-is. Works on local dirs and remote URLs.

**`tool=upgrade`** — legacy → 3D Tiles 1.1 with per-tile content conversion (`packages/3dtiles-tools/upgrade.js`):
- **JSON-level:** `asset.version` → `1.1`, legacy `content.url` → `uri` (older 1.0/0.0 tilesets).
- **`b3dm` → `glb`:** a b3dm is a header + feature/batch tables + an embedded GLB — extracted by slicing
  to the GLB (zero-copy where possible).
- **`pnts` → `glb`:** parsed and re-encoded to a glTF `POINTS` GLB (native fast builder; POSITION /
  POSITION_QUANTIZED, RGBA/RGB/RGB565/CONSTANT_RGBA, RTC_CENTER → node translation).
- **glTF 1.0 → 2.0:** if the embedded GLB is **version 1** (legacy `pg2b3dm`/older exporters), it is
  upgraded to glTF 2.0 via **`gltf-pipeline`** (`processGlb`) so Three.js/3DTRjs can load it (CesiumJS
  reads glTF 1.0 natively, Three.js does not).
- **`CESIUM_RTC` baking:** because we serve a plain GLB (bypassing each renderer's native b3dm/RTC
  handling), the b3dm's `CESIUM_RTC.center` (an ECEF offset) is folded into a wrapper **node
  translation** and the extension stripped. The center is **pre-rotated by the inverse glTF up-axis**
  (RX−90°: `(x,y,z)→(x,z,−y)`) so the renderer's Y-up→Z-up RX+90° restores the true ECEF position —
  otherwise the ~6378 km-magnitude center is itself rotated 90° and the geometry lands thousands of km
  away (correct bounding boxes, empty tiles). The small relative mesh vertices still get RX+90°, as in
  native b3dm.

`i3dm`/`cmpt` content and full PBR material rebuilds are deferred to `3d-tiles-tools`
(`upgrade --targetVersion 1.1`).

**`viewer.html`'s "⚙ Tools" mode groups a third operation, `packages`,** alongside these two for UX —
but it isn't a `/3dtiles-tools?tool=…` value at all: it routes to the *separate*
**`/3dtiles-self-contained`** endpoint (a `.3tz`/`.3dtiles` package → a standard streamed 3D Tiles
tileset — see
["`/3dtiles-self-contained` — serve `.3tz` / `.3dtiles` packages in-place"](/docs/guide/architecture-the-materialization-continuum-cache-none-hierar#3dtiles-self-contained--serve-3tz--3dtiles-packages-in-place)
in the architecture doc), not a tileset-level transcode. The grouping is "pick an operation to demo,"
not an architectural claim that `packages` lives under `/3dtiles-tools`.

**Doable but low value (noted, not planned):**
- **Point-budget / downsample proxy** — serve fewer/decimated tiles to weak clients. Marginal: a
  capable renderer (CesiumJS / 3DTilesRendererJS) already loads only what its SSE budget needs.
- **Mesh → points** — emit only vertices of a mesh tileset. Niche (loses the surface; render-time can
  approximate), listed for completeness.

For full offline pipelines (merge, `mergeJson`, `upgrade`, `b3dmToGlb`/`pnts`/`i3dm`/`cmpt` → glTF),
use **[`3d-tiles-tools`](https://github.com/CesiumGS/3d-tiles-tools)** — the canonical CesiumGS toolbox.

## When a read fails

This holds for every format, as every source read goes through one layer (`packages/core/source-fetch.js`), and a test runs
the same rules against each format (`stream-contract.test.js`):

| The host | What happens |
|---|---|
| Fails once: a reset, a timeout, a 429, a 5xx | Retried, three tries in all, with a backoff |
| Keeps failing | `/stream` answers **502**, never a 200 with an empty body or an empty tile. A client can ask again |
| Says the file is not there: 403, 404, 410 | `/stream` answers **404**. A subtree or a tile the source lacks stays a gap in the source |
| Gets a burst | Paced at 32 requests at a time per host (`TILED_RANGE_MAX_PER_HOST`), not refused |
| Fails under load: a 429, a 503, a reset | The cap for that host halves, down to 4, and climbs back by one for every window of reads that all passed |
| Ignores `Range` and sends the whole file | The right bytes are cut out of it |

A dataset whose first read failed is tried again a minute later, not marked as broken until the server restarts. A hierarchy
is complete or an error: subtrees wait for the chunks they cover, also those another request is already reading. One
exception: on a huge I3S layer, a viewer gets what the first 3 seconds of node pages hold, marked
`asset.extras.hierarchyIncomplete`, so that it opens quickly. An export asks for the whole tree, as does `cache=hierarchy`.
