The splat formats this repo converts (streamed SOG, LCC, RAD, GeoSplats) and the one it writes (SPZ v2 inside
`KHR_gaussian_splatting_compression_spz_2` GLBs) are also handled by a handful of general-purpose tools. This page
is the survey behind our choices, taken on 2026-11-08 from each project's repository, README and published package.
What we use: [`@playcanvas/splat-transform`](https://github.com/playcanvas/splat-transform) 3.x to decode SOG
(streamed-SOG chunks and GeoSplats octants) and, on the extract endpoint, to read SPZ and write SPZ, SOG, PLY and
glTF; our own readers for LCC and RAD and our own SPZ v2 writer (the
[formats guide](/docs/guide/supported-formats#where-the-code-is-our-own-and-why) says why).

## splat-transform 2.6 to 3.x, as it touched this repo

3.0 (pull request [#276](https://github.com/playcanvas/splat-transform/pull/276)) rewrote the library around lazy
*chunk sources* backed by a pool, instead of whole tables. The "7× faster" of its announcement is one benchmark
there: a 10-million-splat PLY read, `--filter-nan`, write, in a fifth of the memory. It says nothing about SOG
decode, which is what we use, and that measured the same before and after (17.4 against 17.8 s on the skatepark
scene; the same bytes out). Loading the module still costs each thread 1.8 s, as it brings the PlayCanvas engine
in at import.

What we changed to move: SOG chunks go through `readSog(fileSystem, 'meta.json')`, which still returns a table
(`readFile` now returns sources); the extract endpoint reads SPZ through `readSpz(source, pool)` and
`materializeToDataTable`; `writeSog` takes an `iterations` count; `MemoryFileSystem.results` holds the output.
`readLcc` and `readLcc2` are no longer root exports (they sit behind `readFile({ inputFormat })`), which does not
matter to us: LCC is decoded by our own reader, and of LCC2 (read since 2026-11-09) we parse the manifest ourselves
and hand each chunk, a bundled SOG, to `readSog`. The read path uses no GPU; `webgpu` (Dawn) is a dependency the
package installs but only the CLI imports. Node 22 or later is required.

### 3.11 and SOG v3 (2026-11-10)

3.11 ([#370](https://github.com/playcanvas/splat-transform/pull/370), proposed in
[#362](https://github.com/playcanvas/splat-transform/issues/362)) writes [SOG version 3](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/)
by default (`--sog-version 2` for older viewers) and reads both. What v3 changes: no `quats.webp`, the rotation is a
24-bit exponential map in the alpha channels of `means_l`, `means_u` and `scales`; the opacity byte is `(b / 204)²`,
up to 1.5625, so a gaussian merged by decimation keeps its mass (`meta.opacity.max` says when some exceed 1);
SH palette labels on 24 bits (262 144 entries from the CLI) and a 4th SH band; optional blind data, `extras` and
`comments`. `lod-meta.json` stays version 1, so a streamed SOG may mix v2 and v3 chunks as SuperSplat publishes new
ones; it may also carry `lodErrors` and per-leaf `errors` (3.3 to 3.7 wrote them). Nothing of the layout reaches
this repo: `readSog` yields the same columns for both, rows in the same order. What does reach it is the opacity:
the table's `opacity` logit is `+Infinity` for exactly 1 and the logit of the largest float below 1 (16.64) for
anything above, with the true value in an `opacity_linear` column. Our tiles are SPZ v2, one alpha byte of [0, 1],
and the viewers of this repo draw no opaque core, so `sogChunk.js` takes `opacity_linear` when it is there and
clamps at 1: a v3 chunk gives the tile its v2 encoding would (the fixtures of `packages/sog-to-3dtiles/test`, one
scene as both versions, agree within a quantization step). The per-leaf `errors`, when a `lod-meta.json` has them,
set the geometric errors of the leaf's LOD chain (`lodMeta.js`); the halving stays otherwise.
